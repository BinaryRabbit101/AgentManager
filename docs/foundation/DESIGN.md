# Foundation — Design

The service skeleton and every cross-cutting concern. Everything in this document is a contract other elements build on; feature elements must not invent parallel storage, config, secret, logging, or lifecycle mechanisms.

Conforms to [architecture.md](../architecture.md) D1–D6. Host is Windows 11, single user, non-admin install.

---

## 1. Storage

### 1.1 Decision

**SQLite for structured state + plain files for personas, transcripts, and avatars.** The brief's leaning is adopted, with a precise boundary:

| Kind of data | Store | Why |
|---|---|---|
| Agent definitions (persona, config, avatar, per-agent skills) | Files (`library/agents/…`) | Portable, diffable, git-versionable, hand-editable, copy-to-clone. This is the user's authored content. |
| Project registry, assignments, sessions, mailboxes, questions, usage, events, remote token hashes | SQLite | Relational, queried by joins and status filters, mutated concurrently, needs transactions and crash-consistency. |
| Session transcripts | Files (`state/transcripts/*.jsonl`) | Append-only, large, streamed and tailed. Would bloat the DB and blow WAL checkpoints for zero query benefit. |
| Logs | Files (`state/logs/*.log`) | See §5. |

The rule of thumb for future elements: **if it is authored by a human and should survive a machine rebuild, it is a file; if it is generated by the system and queried by the system, it is a row; if it is an append-only stream, it is a file referenced by a row.**

Rejected alternatives: single SQLite store (loses git-versioning of the roster, which the roster element explicitly wants, and turns transcripts into a vacuum problem); all-files (mailbox delivery, question inbox status, and per-session token accounting all need atomic multi-row updates and indexed queries — file-based hive messaging was fine for munder-difflin's single loop but not for concurrent assignments); a server database (absurd operational cost for a single-user desktop app).

### 1.2 Roots and directory layout

Three distinct roots, all resolvable without admin rights:

| Root | Default | Config key | Contents |
|---|---|---|---|
| Install root | `%LOCALAPPDATA%\Programs\AgentManager\` | n/a | Immutable program files, packaged defaults, PowerShell scripts. Never written at runtime. |
| Data root | `%LOCALAPPDATA%\AgentManager\` | `dataRoot` (env `AGENTMANAGER_HOME`) | Everything the service owns. |
| Library root | `<dataRoot>\library\` | `library.root` | Authored content. May be relocated to e.g. `%USERPROFILE%\Documents\AgentManager-Library` and `git init`'d by the user. |

```
%LOCALAPPDATA%\Programs\AgentManager\      # install root
  app\                                     # built core + web bundle
  node\                                    # bundled Node runtime
  config\
    defaults.json                          # layer 1 (read-only)
    edition.home.json                      # layer 2 (read-only)
    edition.work.json                      # layer 2 (read-only)
  scripts\*.ps1                            # install/setup scripts
  launch-core.vbs                          # windowless launcher stub (§4.3)

%LOCALAPPDATA%\AgentManager\               # data root
  config\
    config.json                            # layer 3, machine-local (contains `edition`)
  library\                                 # git-friendly, user-authored; contents owned by roster
    roster.json                            # roster-level metadata (schemaVersion, seededAt)
    agents\<agent-id>\
      agent.json                           # schema owned by roster
      persona.md
      avatar.png
      roles\                               # optional per-collaboration-role persona addenda
      skills\                              # optional per-agent skills
      .claude-plugin\plugin.json           # generated by roster; makes the folder a local plugin
    .archive\<agent-id>-<timestamp>\       # soft-deleted agents
    .gitignore                             # seeded; excludes nothing by default
  state\
    agentmanager.db                        # SQLite (WAL: -wal, -shm siblings)
    backups\agentmanager-<schemaVersion>-<ts>.db
    transcripts\<YYYY>\<MM>\<session-id>.jsonl
    logs\core.log, core-<YYYYMMDD>-<n>.log, access.log
    secrets\secrets.json                   # DPAPI-protected envelope (§3)
    secrets\master.key                     # only in keyfile fallback mode
  worktrees\<project-slug>\<assignment-id-8>\   # git worktrees (root configurable, §2.3 `projects.worktreesRoot`)
  run\
    core.lock                              # exclusive-handle single-instance lock
    core.port                              # {"port":7477,"pid":1234,"startedAt":"..."}
  cache\                                   # regenerable; safe to delete
```

`run/` and `cache/` are recreated on boot if missing. Deleting `state/` loses history but not the roster. Deleting `library/` loses the roster but leaves history intact and orphan-tolerant (§1.4).

### 1.3 SQLite engine rules

- Driver: **better-sqlite3** (synchronous, in-process, no pool). One process — the core — ever opens the file. Electron and remote browsers reach data through HTTP/WS, never the file. This sidesteps Windows file-locking pain entirely and gives a single writer for free.
- Pragmas at open: `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`, `busy_timeout=5000`.
- All writes go through the `Store` module. Feature modules receive **repository objects** (`ctx.store.sessions`, `ctx.store.questions`, …), not the raw handle. No feature module composes SQL against another element's tables; cross-element reads go through the owning repository. The foundation-shipped repositories **are** the sanctioned cross-element read path — an element needing another element's data calls a repository method (adding one if it does not exist yet), never a hand-written join against a foreign table.
- Migrations: numbered SQL files `migrations/0001_init.sql`, `0002_….sql`, applied in order inside one transaction on boot, tracked by `PRAGMA user_version`. Before applying any migration the DB is copied to `state/backups/`. Migrations are forward-only; there is no down path in v1.
- Integrity: `PRAGMA quick_check` on boot; failure is fatal and reported with the backup path to restore from.
- IDs: application-generated `ULID` strings (sortable, opaque, safe in filenames and URLs). No autoincrement integers in cross-element contracts.
- Time: all timestamps stored as ISO-8601 UTC strings (`2026-08-16T10:35:00.000Z`). Human-readable in a DB browser, sorts lexicographically, no timezone ambiguity.
- Naming: **table names are plural** (`projects`, `sessions`, `work_items`). Join tables are the plural of the thing they hold (`assignment_members`, `work_item_assignments`). No exceptions — a mixed convention costs more in lookups than it ever saves in typing.

#### Element-owned migrations

Foundation ships only the core set (§1.4). Every other table belongs to the element that owns it, and elements ship their own migrations:

- A module declares `migrations/<moduleId>/NNNN_<name>.sql` alongside its source.
- The migration runner applies foundation's core set first (tracked by `PRAGMA user_version`), then each module's set **in module topological order** — the same order `dependsOn` produces at start-up, so a module's tables exist before any module that depends on it runs.
- Module migrations are tracked per module in `schema_migrations(module TEXT, version INTEGER, applied_at TEXT, PRIMARY KEY (module, version))`. `user_version` stays reserved for foundation's own set; the two mechanisms never contend.
- Everything else is unchanged: one transaction per migration, pre-migration backup, forward-only, fatal on failure.

This is the mechanism by which `agent_ui_state` (roster), `project_default_agents` / `work_items` / `work_item_assignments` / `workspace_leases` (projects) and their successors reach the database without foundation having to know about them.

### 1.4 Core table inventory (v1)

Foundation ships these tables in `0001_init.sql` because more than one element touches them. Column lists are the minimum contract; owning elements may add columns via later migrations.

**Element-owned tables live in element migrations** (§1.3): foundation ships only the tables more than one element touches. A table read by exactly one element belongs to that element's own migration set, not here.

| Table | Owner | Purpose / key columns |
|---|---|---|
| `schema_meta` | foundation | `key`, `value` — schema version, install id, created_at. |
| `agents` | roster (index only) | Mirror of `library/agents/*`: `id` (PK, = folder name), `name`, `specialty`, `model` (flattened string — the resolved `model.primary` alias or id, not the roster object), `is_overseer`, `archived_at`, `source_path`, `content_hash`, `indexed_at`. **Files are truth**; this table is a rebuildable index so other tables can join and filter. | `assignment_members` | orchestrator | `assignment_id`, `agent_id`, `role` (`implementer`\|`architect`\|`skeptic`\|`reviewer`\|`overseer`), PK on the pair. These five strings are the v1 role vocabulary everywhere — roster's `capabilities.roles`, its `roles/<role>.md` addendum files, and orchestrator's patterns all key on exactly them. |
| `sessions` | runner | `id`, `assignment_id` (NOT NULL), `agent_id`, `project_id`, `status` (`queued`\|`running`\|`paused`\|`done`\|`failed`\|`interrupted`\|`orphaned`), `sdk_session_id`, `model`, `permission_mode`, `origin` (`local`\|`remote`), `transcript_path`, `transcript_bytes` (running byte count maintained by the transcript writer, §1.5), `summary` (one-line denormalized digest so a timeline renders without opening a transcript), `pinned` (exempts the session from transcript pruning), `started_at`, `ended_at`, `exit_reason`. | `messages` | orchestrator | `id`, `assignment_id`, `from_agent_id`, `to_agent_id` (NULL = broadcast), `kind`, `body`, `payload_json`, `created_at`, `delivered_at`, `read_at`. A mailbox is a query: `to_agent_id = ? AND read_at IS NULL ORDER BY created_at`. Indexed accordingly. |
| `questions` | orchestrator | `id`, `assignment_id`, `session_id`, `kind` (`question`\|`approval_gate`\|`budget_halt`), `status` (`open`\|`answered`\|`cancelled`\|`expired`), `prompt`, `options_json`, `created_at`, `answered_at`, `answer_json`, `answered_via` (`local`\|`remote`). Persisted, so an open question survives a core restart and is answerable from the tailnet browser (ui's "never stranded on the desktop"). |
| `question_recommendations` | orchestrator | `question_id`, `agent_id`, `stance`, `rationale`, `strength`. Carries the per-agent recommendation the UI renders; the shape of `strength` is orchestrator's call. |
| `events` | foundation | `id`, `ts`, `type`, `session_id`, `assignment_id`, `project_id`, `agent_id`, `payload_json`. Append-only structured event spine: every bus event with `persist: true` lands here. Powers UI replay after reconnect and post-hoc debugging. Retention: 30 days or 200k rows, pruned on boot. |
| `remote_tokens` | remote | `id`, `label`, `device`, `token_hash`, `token_prefix`, `created_at`, `last_used_at`, `expires_at`, `revoked_at`. Table exists in both editions (harmless); only the remote module reads it. Only hashes are stored (§3.4). |
| `settings` | foundation | `key`, `value_json`, `updated_at`. Runtime-mutable state that is *not* configuration — e.g. current remote-enabled flag, per-agent remote allowance, last-seen plan-window reset. Foreign keys are declared with `ON DELETE RESTRICT` for `projects`/`assignments` (deleting a project with history is refused; archive instead) and `ON DELETE CASCADE` for child rows (`assignment_members`, `question_recommendations`, `usage_events`). `sessions.agent_id` deliberately has **no** FK to `agents` — deleting an agent from the library must not destroy its session history; the UI renders unknown agent ids as "deleted agent".

Because there is no FK, roster's hard-purge guard ("purge only when no session references the agent", roster §9.3) cannot lean on the database to refuse the delete. Foundation therefore ships `sessions.countByAgent(agentId): number` on the sessions repository, backed by the index on `sessions(agent_id)`, as the sanctioned way for roster to ask. A purge attempted while that count is non-zero is refused.

**Repository methods foundation ships beyond plain CRUD**, because more than one element needs them and §1.3 forbids hand-written joins against a foreign table:

| Repository | Method | For |
|---|---|---|
| `sessions` | `countByAgent(agentId): number` | roster's purge guard (above). |
| `settings` | `listByPrefix(prefix): Array<{ key, value, updatedAt }>` | a prefix scan over the key space. Remote stores one row per agent under `remote.agentAccess.<id>` (remote §6.1) so that granting and revoking are independent writes rather than a read-modify-write over one JSON blob; the expiry sweep and the list endpoint both need the scan (remote §13, R2). |
| `settings` | `deleteByKey(key): void` | absence *is* the disabled state for those rows, so revocation deletes rather than rewrites. |

### 1.5 Transcripts

One JSONL file per session, path `state/transcripts/<YYYY>/<MM>/<session-id>.jsonl`, recorded in `sessions.transcript_path`. **This layout is the single authority** — no element addresses transcripts by any other scheme, and none derives a path from a project slug or any other renameable thing. Each line is one structured SDK event (`{seq, ts, type, …}`). Written append-only with an fsync every N lines or 2 s (whichever first). Readers may tail from a byte offset, which is how the UI resumes a live session view cheaply.

The transcript writer maintains `sessions.transcript_bytes` as it appends, so any element needing the size of a set of transcripts sums a column instead of walking directories. This is what makes projects' per-project size cap (`SUM(transcript_bytes)` over the project's sessions) a single indexed query rather than a filesystem crawl over a tree that is not grouped by project.

Retention is a projects-element policy decision; foundation guarantees only that transcripts are addressable by session id, safe to delete out from under the DB (path NULLed on prune → UI shows "transcript pruned"), byte-accounted, and never contain secrets (§3.5).

## 2. Configuration and editions

### 2.1 Layers and precedence

Layered, not single-file. Lowest to highest precedence:

1. **`<install>/config/defaults.json`** — shipped, read-only. Every key has a value here; this file is the documentation of what is configurable.
2. **`<install>/config/edition.<edition>.json`** — shipped, read-only. Only the deltas that define an edition.
3. **`<dataRoot>/config/config.json`** — machine-local, written by the installer and editable by the user. Contains `edition` plus any local overrides.
4. **Environment variables** — `AGENTMANAGER_<PATH_WITH_UNDERSCORES>` (e.g. `AGENTMANAGER_HTTP_PORT`, `AGENTMANAGER_RUNNER_MAXCONCURRENT`), parsed as JSON when the value parses as JSON, otherwise as a string.
5. **CLI flags** — `--set http.port=7480`, `--edition work`, `--data-root <path>`. Highest precedence, for debugging and one-off runs.

Deep-merged object by object; arrays replace rather than concatenate. The merged result is validated once against a **zod** schema. Validation failure is fatal at boot with a per-key error report — a service that starts on a malformed config is worse than one that refuses to.

**Modules contribute config sub-schemas**, symmetrically with element-owned migrations (§1.3): a module declares a zod sub-schema for its own key namespace and the defaults that go with it, and the loader composes them into the one schema it validates against. §2.3 is therefore the v1 inventory of the composed result, not a hand-maintained list foundation owns alone.

`AGENTMANAGER_HOME` is resolved before layer 3 (it locates layer 3) and is the one setting that cannot live in a config file.

### 2.2 How edition is expressed

A single key: `edition: "home" | "work"`.

- Written into `config.json` by `Install-AgentManager.ps1 -Edition <home|work>`; the installer prompts if not supplied.
- Overridable per-process by `AGENTMANAGER_EDITION` or `--edition` (used for tests and for temporarily running the work profile at home).
- **Default when unset is `work`.** Fail closed: an unconfigured install must never open a remote listener. A missing edition is logged as a warning at boot.
- `edition.work.json` sets `modules.remote.enabled: false`, `http.bind: "127.0.0.1"`, `auth.mode: "env"`, `policy.allowPermissionElevation: false`, and a lower default `runner.maxConcurrent`.
- `edition.home.json` sets `modules.remote.enabled: true`, `remote.bind: "tailscale"`, `auth.mode: "subscription"`, `service.autostart: true`.
- The schema rejects `edition: "work"` combined with `modules.remote.enabled: true`. Edition is not merely a set of defaults the user can undo — it is an invariant enforced at validation *and* at bind time (§6.3).

### 2.3 Key inventory (v1)

```jsonc
{
  "edition": "work",
  "dataRoot": null,                     // null = %LOCALAPPDATA%\AgentManager
  "library":  { "root": null, "watch": true },
  "http":     { "bind": "127.0.0.1", "port": 7477 },
  "remote":   { "bind": "tailscale", "port": 7478, "hostnameHint": null },
  "modules":  { "remote": { "enabled": false }, "orchestrator": { "enabled": true } },
  "runner":   { "maxConcurrent": 2, "queueLimit": 50, "defaultModel": "sonnet" },
  "projects": {
    "root":          null,              // null = %USERPROFILE%\Documents\AgentManager\projects
    "worktreesRoot": null,              // null = <dataRoot>\worktrees
    "browseRoots":   null               // null = [ %USERPROFILE%, projects.root ]
  },
  "agentEnv": {                         // added to every agent child process environment
    "CLAUDE_CODE_DISABLE_AUTO_MEMORY": "1",   // auto-memory is read regardless of settingSources
    "CLAUDE_CONFIG_DIR": null                 // null = <dataRoot>\state\claude-config; never the user's own
  },
  "policy":   {
    "allowPermissionElevation": true,   // may a project widen past the roster baseline at all? (§ roster 6.2)
    "globalDeny": []                    // permission rules denied everywhere, un-overridable by any layer
  },
  "auth":     { "mode": "subscription" },       // subscription | env | bedrock
  "secrets":  { "provider": "auto" },           // auto | dpapi | keyfile | env
  "logging":  { "level": "info", "maxFileMB": 10, "maxFiles": 10, "retentionDays": 14 },
  "service":  { "autostart": false, "shutdownGraceSeconds": 20 },
  "retention":{ "eventDays": 30, "eventMaxRows": 200000,
                "transcriptDays": 90, "transcriptCapMb": 500 }   // transcript values are the per-project defaults
}
```

Ports 7477/7478 are unassigned by IANA and configurable; the actual bound port is always published in `run/core.port` so clients never guess.

Two of these are edition levers rather than preferences. `edition.work.json` sets `policy.allowPermissionElevation: false` — a work machine does not get a per-project escape hatch past an agent's permission ceiling, and roster's compiler refuses the elevation (with a diagnostic) rather than silently applying it. `policy.globalDeny` is the matching positive lever: rules listed there are unioned into every compiled deny set and no layer can remove them, which is how a work edition pins "never `Bash(git push*)` from this machine" regardless of what any agent, project, or assignment says. Both are read by roster's `compilePermissions`, which is the only composer (roster §6.2).

A third edition lever lives in orchestrator's contributed sub-schema rather than the block above: `edition.work.json` sets **`orchestrator.notify.enabled: false`**, so away-notifications are **off by default in the work edition**. Outbound push from a work machine is a policy decision, not a preference — the home edition defaults it on (orchestrator §10, §17 R5). The channel's credential is a secret, not config (§3.3, `notify.ntfy.topicUrl`).

### 2.4 Reading config

Modules receive a frozen, typed `AppConfig` on their context. Config is **immutable for the process lifetime** — changing it requires a restart. Anything that must change at runtime (remote enabled, per-agent remote allowance, log level) is `settings` (§1.4) or an explicit runtime API, not config. This removes an entire class of "half-reloaded state" bugs.

`GET /api/config/effective` returns the merged config with a `source` annotation per key (which layer won) and secrets redacted. This is how the UI knows the edition and hides remote controls, and how support diagnostics work.

## 3. Secrets on Windows

### 3.1 Decision

A **`SecretStore` service with a DPAPI-backed default and an explicit fallback chain**, selected by `secrets.provider`:

1. **`dpapi` (default, chosen provider).** Secrets are encrypted with Windows DPAPI at `CurrentUser` scope plus a fixed application entropy string, via the `win-dpapi` native binding called in-process. The ciphertext envelope is stored as base64 in `state/secrets/secrets.json`. Only the installing Windows user on this machine can decrypt it; copying the file to another machine or user yields nothing. No admin rights, no extra service, no plaintext on disk.
2. **`keyfile` (automatic fallback).** If the native binding fails to load (ABI mismatch after a Node/Electron upgrade is the realistic failure), the store falls back to AES-256-GCM with a 32-byte random key at `state/secrets/master.key`, written with an ACL granting the current user only and inheritance disabled. A `WARN` is logged and a degraded-security flag is surfaced in `/api/health` so the UI can show it. This is weaker (anything running as the user can read the key) but keeps the service running instead of bricking it.
3. **`env` (development, and any install that must store nothing).** Secrets are read from the process environment and never persisted. Note what this is *not*: the work edition (§2.2) sets **`auth.mode: "env"`**, not `secrets.provider: "env"` — model credentials come from the workplace's environment (`ANTHROPIC_API_KEY` or Bedrock), while `secrets.provider` keeps its `dpapi`-with-`keyfile`-fallback default, because the work edition still has non-auth secrets to hold (a project's env entries, an MCP server's token) and nothing is gained by refusing to protect them. Selecting `env` explicitly is a deliberate override, not an edition consequence.

Rejected: **Windows Credential Manager** — per-item 2.5 KB limit, awkward Node access (also a native module, so no dependency saving), and it surfaces entries in a UI users prune by accident. **Plain `.env`** — plaintext at rest and one careless `git add` from a leak. **Shelling out to PowerShell `ConvertFrom-SecureString`** — DPAPI by the standard Windows idiom, but CLAUDE.md restricts PowerShell to install/setup scripts, and piping secrets through a child process at runtime adds an exposure surface for no gain.

### 3.2 Interface

```ts
interface SecretStore {
  get(key: SecretKey): Promise<Secret | undefined>;   // Secret.toString() === "[redacted]"
  set(key: SecretKey, value: string): Promise<void>;
  delete(key: SecretKey): Promise<void>;
  list(): Promise<Array<{ key: SecretKey; setAt: string; preview: string }>>; // preview = last 4 chars
  provider: 'dpapi' | 'keyfile' | 'env';
}

/** The read-only face handed to consumers that resolve refs but must never write. */
export type SecretResolver = Pick<SecretStore, 'get'>;
```

`SecretResolver` is the type every other element codes against — roster's `compileSession` takes one, projects' env resolution takes one — so no feature module holds a handle that can `set` or `delete`.

Secret values are wrapped in a `Secret` type whose `toString`, `toJSON`, and `util.inspect` all return `[redacted]`, so an accidental log or API serialization leaks nothing. Only `.reveal()` yields the plaintext, and it is called in exactly two authorized places:

1. **Roster's option compiler** (roster §13), building the agent child process's environment and MCP server configs — the one place `secretRef` values become real strings.
2. **Runner's `attachAuthEnv()`** (runner §3.4), injecting `claude.oauthToken` into the SDK child environment — one key, one function, consistent with §3.3's key assignment.

The remote module is deliberately **not** on this list: bearer verification never reads a stored secret. It hashes the token the client presented and constant-time-compares it against `remote_tokens.token_hash` (§3.4), so there is nothing to reveal (remote §13, R5).

Any third call site is a review failure, not a judgement call.

### 3.3 Key namespace (v1)

| Key | Set by | Used by |
|---|---|---|
| `claude.oauthToken` | `Setup-Auth.ps1` / UI settings | runner (`CLAUDE_CODE_OAUTH_TOKEN` in the SDK process env) |
| `anthropic.apiKey` | env only, work edition | runner |
| `mcp.<serverId>.<field>` | roster UI | roster's option compiler, resolving a per-agent MCP server's `env`/`headers` refs at session start (roster §10, §13 — the same authorized `.reveal()` site as the row below; runner never touches these) (answers roster's open question: MCP credentials live here, referenced from `agent.json` by key name, never inlined in the agent file — so the library stays git-safe) |
| `project.<projectId>.<name>` | projects UI | roster's option compiler, resolving a project's env entries at session start (projects §1.4). Keyed by project id, not slug, so a rename cannot orphan a secret. |
| `notify.<channel>.<field>` | notification settings UI | orchestrator's notifier (orchestrator §10). v1 uses `notify.ntfy.topicUrl` — an ntfy topic URL is a capability URL, so possession of it is the credential and it belongs here rather than in config. Remote's away-notification path reads the same key (remote §7.4). |

Roster's `agent.json` may contain `{"secretRef": "mcp.gmail.token"}` but never a credential value; the `secretRef` schema is roster's (roster §10) and this document does not restate it. A library or project record containing something that looks like a live credential is rejected at load with a clear error — and "looks like a live credential" is **exactly** roster §10's rule, not a second heuristic: any `env` or `headers` key matching `*TOKEN*` / `*KEY*` / `*SECRET*` / `*PASSWORD*` / `AUTH*` must carry `{ secretRef }` rather than a literal string.

### 3.4 Remote bearer tokens are not stored

Bearer tokens are generated (32 random bytes, base64url), **shown to the user exactly once**, and stored only as `sha256(token)` in `remote_tokens.token_hash` with a 6-character display prefix. Verification is a constant-time hash comparison. Consequence: a token cannot be recovered, only revoked and reissued — which is the correct property for a credential that grants remote agent execution, and it means the compromise of `secrets.json` does not yield remote access.

### 3.5 Keeping secrets out of git and logs

- All secrets live under `dataRoot`, which is outside any repository. The repo's `.gitignore` already covers `.env` and `*.local.json` as a second line of defence.
- The logger redacts by key path and additionally regex-scrubs `sk-ant-[A-Za-z0-9_-]+`, `Bearer [A-Za-z0-9._~+/-]{16,}`, and the known token key names from every message and payload before it is written (§5.4). Redaction happens at write time, so the in-memory ring buffer served to the UI is already clean.
- Transcript writing applies the same scrub, because agent output can echo an environment variable.
- Secrets are passed to SDK child processes through the environment block only — never a command line (visible in Task Manager), never a temp file.
- Startup check (architecture D2): if `ANTHROPIC_API_KEY` is present in the environment while `auth.mode === "subscription"`, log a `WARN` and raise a persistent health warning that the UI displays, because it silently overrides subscription auth.

## 4. Service lifecycle on Windows

### 4.1 Decision: headless core, Electron is a pure client

The core is an independent long-running process. Electron never owns it.

Why: remote start/stop must work while the desktop app is closed (D5 and the remote element's whole premise); sessions must survive a UI crash or restart; one owner of the SQLite file means one writer; and it makes Electron and the tailnet browser literally the same client against the same API (D3), which is the cheapest way to keep them from diverging.

Electron's role: on launch, read `run/core.port`, probe `GET /healthz`. If nothing is listening, spawn the core **detached** (`detached: true`, stdio ignored) and poll for readiness; if it is listening, just connect. Closing the Electron window (or quitting from the tray) never stops the core. An explicit "Stop background service" tray item exists for the user who wants it.

### 4.2 Single instance, discovery, shutdown

- **Single instance**: the core opens `run/core.lock` with an exclusive handle held for its lifetime. A second instance fails to acquire, prints the running port from `run/core.port`, and exits 0. This is more reliable on Windows than PID files, since the handle dies with the process even on a hard kill.
- **Discovery**: after binding, the core writes `run/core.port` (`{port, pid, startedAt, edition}`) and deletes it on graceful exit. A stale file whose `/healthz` does not answer is ignored and overwritten.
- **Graceful shutdown** on SIGINT/SIGTERM/`POST /api/service/shutdown`: stop accepting new sessions and HTTP connections → ask the runner to interrupt in-flight sessions and persist resume state → stop modules in reverse dependency order with a per-module timeout → WAL checkpoint and close the DB → release lock and delete `run/core.port`. Budget: `service.shutdownGraceSeconds` (default 20), after which the process exits anyway.
- **Boot reconciliation**: modules register boot tasks that run after storage is up and before the listener binds. Foundation guarantees the hook and the ordering; the runner uses it to move `running` sessions from a previous life to `orphaned` and decide what is resumable.

### 4.3 Autostart without admin rights

**Task Scheduler, registered in the current user's context** — the only mechanism that is non-admin, survives reboot, supports restart-on-failure, and runs before/independently of any app window.

```
Task name:  \AgentManager\AgentManager Core
Trigger:    At log on of <current user>
Action:     wscript.exe "<install>\launch-core.vbs"
Principal:  current user, RunLevel = Limited, "Run only when user is logged on"
Settings:   RestartCount=3, RestartInterval=1min, ExecutionTimeLimit=0,
            DisallowStartIfOnBatteries=false, StopIfGoingOnBatteries=false,
            MultipleInstances=IgnoreNew, StartWhenAvailable=true
```

`launch-core.vbs` is a three-line stub that runs `<install>\node\node.exe <install>\app\main.js` with window style 0, because a Task Scheduler action running a console executable in an interactive session flashes a console window at every logon. (A packaged windowless launcher executable replaces the stub post-v1; the stub is the simplest thing that works and needs no build tooling.)

Rejected: **NSSM / `sc.exe` Windows service** — requires admin and, run as SYSTEM or a service account, breaks DPAPI CurrentUser secrets and Tailscale's per-user context. **Startup-folder shortcut** — no restart-on-failure, no logging of start attempts, trivially disabled by accident. **Electron-owned** — contradicts §4.1.

Registered by default in the **home** edition (`service.autostart: true`) because remote access while the app is closed is the point. Default **off** in the **work** edition — a work machine should not have a background agent runner starting at logon unasked; Electron starts the core on demand there. Either way it is one config key plus `Register-Autostart.ps1`.

### 4.4 PowerShell install/setup scripts

All under `<install>\scripts\`, all non-admin, all idempotent (safe to re-run), none taking secrets as parameters.

| Script | Responsibilities |
|---|---|
| `Install-AgentManager.ps1 -Edition <home\|work> [-DataRoot <path>] [-NoAutostart]` | Verify Windows/Node prerequisites; create the data root tree and tighten its ACL to the current user — **including creating and ACLing the library directory, and nothing further inside it**; write the initial `config/config.json` with the chosen edition; run the DB migration to create the schema; register autostart (unless `-NoAutostart` or work edition); create Start-menu and optional desktop shortcuts; start the core and wait for `/healthz`; print the local URL and next steps. The library's *contents* — `git init`, `.gitignore`, `roster.json`, and any seeded agents — are roster's on first run (roster §2.1), so there is exactly one component that knows the library's shape. |
| `Setup-Auth.ps1` | Run `claude setup-token` interactively, read the resulting token **from the console into a SecureString** (never echoed, never a parameter), pipe it over stdin to `agentmanager secrets set claude.oauthToken --stdin`, verify with a trivial SDK round-trip, and report success without printing the token. Also warns if `ANTHROPIC_API_KEY` is set in the user or machine environment. |
| `Register-Autostart.ps1` / `Unregister-Autostart.ps1` | Create/remove the scheduled task described in §4.3. Split out so autostart can be toggled without reinstalling. |
| `Test-AgentManagerHealth.ps1` | Diagnostics for support: edition, resolved data root, task state and last run result, listening ports, `/healthz` payload, `PRAGMA quick_check`, secret provider in use, presence of `ANTHROPIC_API_KEY`, Tailscale interface detection (home edition), and the last 50 log lines. Prints a copy-pasteable summary. |
| `Uninstall-AgentManager.ps1 [-RemoveData]` | Stop the core, unregister the task, remove shortcuts and install root. Keeps the data root unless `-RemoveData` is given explicitly, and refuses to delete a library root that lives outside the data root. |

Invoked as `powershell -ExecutionPolicy Bypass -File …`. Scripts do orchestration only — every action they take (create schema, set a secret, check health) is also available through the core's CLI or API, so nothing is PowerShell-only (D1).

## 5. Logging

### 5.1 Format and streams

**JSON Lines**, one object per line, via **pino** (the only logging dependency). Every record carries `ts` (ISO-8601 UTC), `level`, `component` (module id), `msg`, and whichever correlation ids apply: `sessionId`, `assignmentId`, `projectId`, `agentId`, `requestId`.

Three streams, deliberately separated:

| File | Contents |
|---|---|
| `state/logs/core.log` | Service logs: boot, module lifecycle, storage, runner decisions, errors. |
| `state/logs/access.log` | One line per HTTP/WS request: method, path, status, duration, origin (`local`\|`remote`), `tokenId`, token prefix, remote peer. Auth failures at `warn`. Separate because remote access needs an auditable trail that is not drowned in debug chatter (D5). |
| `state/transcripts/*.jsonl` | **Not logs.** Agent conversation content lives in transcripts and is never duplicated into `core.log`. |

`tokenId` is the `remote_tokens.id` of the credential that authenticated the request — **never the token itself**, and never a substitute for it. The 6-character `token_prefix` stays for human recognition, but prefixes can collide and are not a stable join key, so incident review joins on `tokenId` (remote §13, R3).

When the core is started from a terminal (dev), a pretty-printed human stream is added on stderr. When started by the scheduled task there is no console, and the file streams are the only output.

### 5.2 Rotation and retention

Size-based rotation at `logging.maxFileMB` (10 MB) → `core-<YYYYMMDD>-<n>.log`, keeping `logging.maxFiles` (10) plus a hard age cap of `logging.retentionDays` (14 days), whichever prunes first. Rotation is checked on write and once on boot, so a machine that is off for a week still cleans up at next start. Worst case on-disk footprint is bounded and documented (~200 MB across both streams).

### 5.3 How the UI reads logs

Through the API, never by reading files. The UI has to work identically over the tailnet, where the filesystem is not reachable.

- The logger tees the last 2000 records into an in-memory ring buffer.
- `GET /api/logs?level=&component=&sessionId=&since=&limit=` serves the ring buffer, falling back to parsing the tail of the rotated files when `since` predates it.
- `GET /api/logs/stream` (SSE) pushes new records live with the same filters.
- `GET /api/logs/download` returns a zip of the current log files for support, and is the only file-shaped endpoint.
- `PUT /api/logs/level` changes the level at runtime without a restart — essential for debugging a remote incident you cannot reproduce locally.

All log endpoints require the same auth as the rest of the API; over the remote listener they additionally require the bearer token, like everything else.

### 5.4 Redaction

Redaction runs inside the pino formatter, before anything reaches disk or the ring buffer: key-path redaction for known secret fields plus the regex scrub of §3.5. Redacting at write time (rather than at read time) means there is no window where a secret sits in a buffer or a file waiting to be filtered.

The redactor additionally scrubs credential-bearing **query-string parameters** from any logged URL or path — `ticket=` and `access_token=` in v1 — replacing the value with `[redacted]` while leaving the parameter name visible. This applies to `access.log` and `core.log` alike, since a request path reaches both. A short-lived ticket is still a credential, and a credential in a log line outlives the request that carried it (remote §13, R3).

## 6. Module system

### 6.1 Shape

Every element is a module with a uniform contract:

```ts
interface Module {
  id: string;                       // 'storage' | 'roster' | 'runner' | 'remote' | ...
  dependsOn: string[];
  critical?: boolean;               // failure to start kills the process (storage, config)
  init(ctx: ModuleContext): Promise<ModuleHandle>;
}

interface ModuleHandle {
  start?(): Promise<void>;
  stop?(): Promise<void>;
  health?(): HealthReport;
}
```

`ModuleContext` is the only thing a module may reach for. It provides: the frozen `AppConfig`; `store` (repositories, §1.3); a child `logger` pre-tagged with the module id; `secrets`; the typed event `bus`; `settings`; `clock` (injectable, so tests are not time-dependent); `registerRoutes(router)` (with optional per-route remote policy metadata, §6.4); `registerBootTask(fn)`; `registerHealthCheck(fn)`; and the service registry `provide(name, api)` / `require<T>(name)`.

Feature modules **never import each other directly**. They communicate through the event bus (fire-and-forget, typed) and through service interfaces published on the registry (request/response). This is what makes the remote module removable without a compile error anywhere else.

### 6.2 Composition root and edition gating

`src/main.ts` builds the module list from config:

```ts
const modules = [storage, secrets, http, roster, projects, runner];
if (config.modules.orchestrator.enabled) modules.push(orchestrator);
if (config.edition === 'home' && config.modules.remote.enabled) {
  modules.push((await import('./modules/remote')).default);   // dynamic import
}
```

The remote module is dynamically imported, so in the work edition its code is never evaluated, its routes never registered, its sockets never created — and a packaged work build can drop the chunk entirely if that ever matters. One codebase, one bundle, a runtime gate (D6). No `#ifdef`-style branching anywhere else in the tree: any code that would want to ask "are we home edition?" instead asks whether a capability is present (`ctx.require('remote')` returns undefined).

Modules are topologically sorted by `dependsOn`, started in order with a per-module start timeout (10 s), and stopped in reverse. A non-critical module that fails to start is logged, marked unhealthy in `/api/health`, and the service continues — a broken orchestrator should not prevent you from reading logs and fixing it. `storage` and `secrets` are critical.

### 6.3 Bind-time invariant

After all modules have started, foundation enumerates every listening socket the process owns and asserts:

- `edition === 'work'` → **every** listener is bound to a loopback address, else the process logs a fatal error and exits.
- `edition === 'home'` → any non-loopback listener must match the address and port the remote module **publishes** as its own via `ctx.require('remote').boundAddress()` (remote §11, R4), which returns `{ address, port, source } | null`. The assertion does not re-derive or infer which listener belongs to remote, and does not itself go looking for the Tailscale interface.

Reading remote's published claim rather than re-deriving the address is the point: the assertion then compares **two independently produced claims about the same socket** — what the OS says is listening, and what the module says it bound — instead of trusting one heuristic twice. A non-loopback listener that no module claims, or one whose claimed address does not match the socket, is fatal. Remote separately re-validates the same address against its Tailscale check immediately before `listen()`.

This turns D5/D6 from a convention into a testable startup assertion that fails loudly, which is exactly what a security boundary needs.

### 6.4 HTTP surface

Foundation owns one route table and one HTTP/WS framework instance. The local listener binds `http.bind` (127.0.0.1). The remote module, when present, mounts **the same route table** on a second server bound to the Tailscale address with bearer-token middleware in front and an `origin: 'remote'` marker on the request context. One API, two listeners — remote's open question about a reduced surface is then a matter of which routes the remote middleware refuses, not a second implementation to keep in sync. Foundation-owned routes in v1: `/healthz`, `/api/health`, `/api/config/effective`, `/api/logs*`, `/api/service/shutdown`, `/api/events` (replay + live stream), and the **static SPA route** below.

**Foundation serves the built SPA.** The web bundle shipped in `<install>\app\` (§1.2) is served by this same HTTP server, on **both** listeners, as one registered static route: the bundle's files at their own paths (`/index.html`, `/assets/*`, favicon, and anything else the build emits), plus an **SPA history fallback** — any `GET` outside `/api/**` that matches no static file returns `index.html` with a 200. Registered `remote: 'allow'`. `/api/**` never falls through to the fallback; an unknown API path stays a JSON 404, so a typo'd endpoint fails as an API error rather than as a page. This is the provider for remote §3.1's first middleware rule, which already bypasses auth for `GET /`, `/assets/*`, `/index.html` and the favicon — that rule described routes nobody had registered (ui §19, R1). The history fallback is load-bearing, not cosmetic: orchestrator's ntfy deep link (`…/questions/:id`, orchestrator §10) and every bookmarked client-side route arrive as a cold `GET` of a path only the SPA router knows, and without the fallback each one 404s on open or reload.

**Per-route remote policy metadata.** `registerRoutes` accepts optional metadata per route, `{ remote: 'allow' | 'deny' }`, **defaulting to `allow`**. A module that adds a route which must never be reachable from the tailnet declares `remote: 'deny'` at the point of registration — next to the code that makes it dangerous — rather than in a list somewhere else that someone has to remember to update. Foundation only records the flag and exposes it on the route table; it enforces nothing itself, because the local listener has no notion of remote (remote §13, R1).

Remote is the consumer. Its policy is **default-allow-authenticated** (remote §3.1): the remote middleware serves every registered route to a valid bearer token *except* those the register marks `remote: 'deny'`, plus remote's own hardcoded pattern list, which stays as a backstop for routes whose author did not think about it. Foundation's own `POST /api/service/shutdown` is registered `remote: 'deny'` — a remote action that can brick the transport it arrived on needs someone at the machine. Defaulting to `allow` is deliberate: an allowlist would make every newly added route silently broken remotely until someone remembered it, which is the drift §6.4 exists to prevent.

**The local listener has no authentication, and that is intended.** `http.bind` is loopback; anything that can reach it is already a process running as the owning Windows user, and such a process can already read the DPAPI-protected secret envelope (§3.1), the SQLite file, and the transcripts directly. Adding a credential to the loopback listener would guard nothing it does not already own, while adding a login step to the Electron shell and a second failure mode to local start-up. **The local OS user is the owner**; Electron and a local browser at `127.0.0.1` are its clients, and they authenticate by being on the machine. Authentication is precisely what the *remote* listener adds on top of this baseline (remote §4), which is why the baseline is stated here rather than assumed (remote §13, R6). The corollary is that the loopback binding is a security control, not a convenience — §6.3's bind-time assertion is what keeps it one.

### 6.5 Event bus

In-process typed emitter. Events are `{type, ts, ids, payload, persist?}`. Events flagged `persist` are written to the `events` table in the same tick they are emitted; all events are fanned out to WS subscribers. This gives the UI one mechanism for both "what happened while I was disconnected" (replay from `events` by id watermark) and "what is happening now" (live stream), which is the difference between a session view that recovers from a dropped tailnet connection and one that does not.

**Subscriptions are filterable** (ui §19, R4). `/api/events` accepts an optional `types=` parameter — a comma-separated list of exact event types or `prefix.*` patterns (e.g. `types=session.started,session.ended,question.*`) — applied identically to the live fan-out and to the `since=` replay, so a reconnect returns the same subset it was streaming. Omitting it keeps the current behaviour: everything. Without a filter, a client holding the global feed also receives the high-volume non-persisted types (`session.delta`, `session.message`, `session.tool.*`, `session.usage`) for **every** running session; a phone on a metered link would pay radio for bytes it discards on arrival, while per-session detail is already available on runner's dedicated `/api/sessions/:id/stream`. Filtering is a subscription concern only — it changes what a socket is sent, never what is emitted, persisted, or replayable.

## 7. Deliberately deferred past v1

- Multi-user / multi-machine: single Windows user, single host. No account model, no roster sync.
- Automatic git commit/push of `library/` — the folder is git-ready, but versioning is the user's to drive.
- Encryption of `agentmanager.db` at rest (SQLCipher). DPAPI protects secrets; the DB holds no plaintext credentials by design (§3.4).
- Log shipping / remote telemetry.
- A true Windows service (admin install), MSI/Squirrel packaging, and code signing.
- Transcript compression and tiered archival.
- Config hot-reload (§2.4) and down-migrations (§1.3).
- Per-device secret scoping and hardware-backed keys.

## 8. Decisions

Every open question from the foundation brief, plus the cross-element questions that are foundation's to answer.

### From the foundation brief

| Question | Decision | Rationale |
|---|---|---|
| SQLite + files split, or single store? | **Split**, per §1.1. | The roster is authored content that must diff, clone, and version in git; assignments/sessions/mailboxes/questions need transactions, joins, and status indexes; transcripts are append-only streams. One store forces two of the three into the wrong shape. |
| Headless core, or Electron owns it? | **Headless core; Electron is a pure client** (§4.1). | Remote start/stop while the app is closed is the product's premise. It also gives one SQLite writer and makes the Electron and tailnet clients identical. |
| One config file or layered? | **Layered**: defaults → edition → machine-local → env → CLI (§2.1). | Editions are literally a config layer, so a layered system makes D6 free. Shipped defaults double as documentation, and the machine-local file stays small enough to read. |
| Non-admin Windows autostart? | **Task Scheduler, at-logon, current-user principal, launched through a VBS stub** (§4.3). | The only mechanism that needs no admin, survives reboot, restarts on failure, and keeps DPAPI CurrentUser secrets and Tailscale's user context working. Services need admin and break both. |

### Cross-cutting decisions other elements asked for

| Question (from) | Decision | Rationale |
|---|---|---|
| Where do agent definitions live? (roster) | Files: `library/agents/<id>/` with `agent.json` + `persona.md`, mirrored into a rebuildable `agents` index table. | Files are truth so git-versioning and duplicate-and-edit work; the index makes joins and roster queries cheap without dual-write risk. |
| Where do MCP/integration credentials live? (roster) | In `SecretStore` under `mcp.<serverId>.<field>`; `agent.json` carries only a `secretRef` key name (§3.3). | Keeps the library git-safe by construction — an agent file can be shared or committed with no credential in it. |
| Where do transcripts live and how do they link to project history? (runner, projects) | `state/transcripts/<YYYY>/<MM>/<session-id>.jsonl`, addressed by `sessions.transcript_path`; project history is a query over `sessions` joined to `assignments`. | Big append-only blobs stay out of the DB; the DB keeps the relationships. Pruning a transcript degrades gracefully instead of corrupting history. |
| Per-session token metering (runner, orchestrator, ui) | `usage_events` append-only deltas + `session_usage` rollup written in the same transaction; assignment totals rolled onto `assignments.tokens_used`. | Budget enforcement needs a single indexed read per check; the UI needs the time series. Writing both in one transaction keeps them from drifting. |
| Assignment records and the "every session belongs to an assignment" rule (orchestrator) | `assignments` + `assignment_members`, with `sessions.assignment_id NOT NULL`; a solo launch creates a trivial assignment. | Enforcing it at the schema level is what makes budgets, scope, and question attribution uniform rather than special-cased. |
| Mailboxes (orchestrator) | Rows in `messages`, mailbox = an indexed query on `(to_agent_id, read_at IS NULL)`; delivery notification rides the event bus. | Atomic-file hives lose ordering and delivery state under concurrent assignments; a table gives both for less code. |
| Question inbox persistence (orchestrator, ui) | `questions` + `question_recommendations` tables, answerable through the shared API from local or remote (`answered_via` recorded). | A question that only exists in memory is stranded by a restart, and one that only exists on the desktop is stranded by the user being out. Persisting it fixes both at once. |
| Edition gating of the remote module (remote) | Dynamic import behind an edition check in the composition root, plus a post-start bind-time assertion (§6.2, §6.3). | Config alone can be edited; an assertion that refuses to run with a non-loopback socket in the work edition is a boundary that actually holds. |
| One API or two? (remote) | One route table, two listeners; the remote listener adds bearer auth and may refuse routes (§6.4). | Two implementations of the same surface drift, and the drift shows up as a remote-only bug at the worst moment. |
| Bearer token storage (remote) | Hash-only (`sha256`) in `remote_tokens`, plaintext shown once (§3.4). | Compromising the secrets file must not yield remote agent execution. Rotation replaces recovery. |
| How does the UI read logs? (ui) | Through `/api/logs` + SSE stream + in-memory ring buffer, never the filesystem (§5.3). | The remote browser has no filesystem access; one path for both delivery modes is one path to keep working. |
| Concurrency cap default (runner) | `runner.maxConcurrent: 2`, configurable; lower default in the work edition. | Rate-limit windows are shared with the owner's own Claude usage (D2); two is enough to feel parallel while leaving headroom, and it is one config key to change. |
| What is config vs. runtime state? | Config is immutable per process; anything the UI toggles lives in `settings` (§2.4). | Removes the whole class of partially-applied-reload bugs, and keeps a config file rewrite from clobbering user toggles. |
