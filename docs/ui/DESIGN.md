# UI — Design

The one web frontend (architecture **D3**): Electron-wrapped as the local Windows app, plain browser
over the tailnet for remote. One codebase, one bundle, two delivery modes.

Conforms to [architecture.md](../architecture.md) D1–D6. This element **consumes** every other
element's pinned contracts — foundation's routes/events/config, roster's agent schema and drafting
API, projects' quick-add and timeline, runner's session lifecycle and transcript tailing, orchestrator's
assignments/questions/conversation, remote's tokens/tickets/grants — and **invents no backend
behaviour**. Where a contract turns out to be unworkable from this side it is raised in §19, never
worked around.

The brief's UX north star is binding and is the thing every decision below is measured against:

> Managing agents must feel **visual and direct, not form-driven**. The roster is a **board of agent
> cards**; assignment is **drag and drop**. Creating an agent and registering a project must each be
> doable in **under a minute** without editing files by hand.

## 1. Stack

### 1.1 Framework: React, confirmed

**React 18 + TypeScript + Vite.** The README's default assumption is adopted rather than re-opened,
and the reasons are specific to this app rather than generic:

- The board is a live, multi-source view over a websocket event feed. React's reconciliation over a
  normalised cache is the boring, well-trodden shape for that, and `dnd-kit` (§5.3) — the only
  drag-and-drop library that gives pointer, touch **and keyboard** sensors with screen-reader
  announcements out of the box — is React-only. Accessibility for the drag gesture is a hard
  requirement of the brief, and it is the single strongest argument in the framework choice.
- Vite gives one command for dev (HMR against a running core) and one for the production bundle that
  the core serves. No second toolchain, no SSR, no server runtime for the frontend at all.
- TypeScript types for every wire shape are generated by hand from the sibling design docs into
  `src/api/types.ts` and are the only place the UI states a backend shape.

Rejected: Svelte/Solid (smaller, but no equivalent accessible DnD primitive and a smaller pool of
worked examples for the streaming-list problem); Next.js or anything with a server (there is already
a server — the core — and D3 says the frontend is served by it); a native Windows UI (kills D3 in one
move).

### 1.2 State management

Two stores, split by whether the data belongs to the server:

| Kind | Mechanism | Examples |
|---|---|---|
| **Server state** | **TanStack Query** — one query key per endpoint, `staleTime` generous because the event feed is what invalidates | roster list, projects, sessions, questions, assignments, usage, config |
| **Client state** | **Zustand**, one small store | theme, connection status, event watermark, drag state, launch-sheet state, unread badges, the remote bearer token handle |

The glue is a single **`EventStream` singleton** (§3.3) that maps bus events onto
`queryClient.invalidateQueries` / `setQueryData`. This is the whole state architecture: **the server
is the source of truth, the event feed is the invalidation signal, and no screen polls.** There is no
Redux, no client-side derivation of anything the server already computes (`disagreement`,
`contested`, project `health`, assignment `outcome`, the fleet `state` vocabulary are all read, never
recomputed — orchestrator §16.1, projects §3.1).

Streaming session content is the one exception: it is high-volume and append-only, so it lives in a
per-session ring buffer inside the Zustand store rather than in the query cache (§9.3).

### 1.3 How the SPA is served

Per foundation §1.2 the built bundle ships in `<install>\app\` beside the core, and **the core serves
it from its own route table** — so both listeners serve the same files and there is exactly one
origin per delivery mode:

- `GET /` and `GET /assets/*` → the built bundle.
- Any other non-`/api` GET → `index.html` (history fallback), which is what makes the ntfy deep link
  `…/questions/:id` (orchestrator §10) and every other bookmarkable route work.
- These paths are unauthenticated on the remote listener by remote §3.1's static-shell bypass — the
  phone must be able to load the app before it can authenticate.

Foundation §6.4 ships exactly this: the static route for the bundle plus the SPA history fallback, on
**both** listeners, registered `remote: 'allow'`, with `/api/**` never falling through to the fallback
so a typo'd endpoint stays a JSON 404 (§19, R1). Nothing else in this design depends on how it is
implemented.

**All API calls are same-origin and relative** (`/api/...`). There is no base URL to configure, no
CORS (remote §9.2 #9 forbids CORS headers outright), and no build-time distinction between the
Electron build and the browser build. **There is one build.**

### 1.4 No external CDNs, ever

The tailnet browser may have no internet route at all. Therefore:

- **No webfonts.** A system font stack (`Segoe UI Variable`/`Segoe UI` on the host, `-apple-system`
  on iOS, system emoji font for avatars). Zero font bytes, and emoji avatars render natively on every
  target.
- **No icon font, no icon CDN.** A hand-picked inline SVG sprite in the bundle.
- **No analytics, no map tiles, no remote images.** The only image the app ever loads from the network
  is an agent avatar from `/api/roster/agents/:id/avatar`, same-origin.
- QR codes are generated **client-side** with a bundled `qrcode` library into inline SVG (§13.2).
- Markdown rendering uses a bundled renderer with HTML disabled and a strict sanitiser; agent output
  is untrusted text.

This is enforced by remote §9.2 #9's strict CSP with no third-party origins — a stray CDN reference
fails at runtime in the browser, so the constraint is testable rather than aspirational (§18, M11).

### 1.5 The Electron shell — exactly these responsibilities and nothing else

Foundation §4.1 is unambiguous: **the core is an independent process and Electron is a pure client.**
The shell is a thin wrapper whose entire job list is:

1. **Discover or start the core.** Read `<dataRoot>\run\core.port` (foundation §4.2), probe
   `GET /healthz`. If nothing answers, spawn the core detached (`detached: true`, stdio ignored) and
   poll for readiness with a visible "Starting AgentManager…" splash and a timeout that surfaces the
   log path. If it answers, just connect.
2. **Create the window** and load `http://127.0.0.1:<port>` — **never `file://`**. Loading over HTTP
   is what keeps the Electron client byte-identical to the tailnet client: same origin model, same
   relative paths, same bundle, no second build (D3).
3. **Tray icon**: Open AgentManager, "N questions waiting" (opens the inbox deep link), Stop
   background service (`POST /api/service/shutdown`), Quit. Closing the window never stops the core.
4. **Single-instance lock** on the app itself; a second launch focuses the existing window.
5. **Native folder picker**, exposed through the preload bridge, because projects §2.1 says Electron
   posts a path from the native dialog while the browser uses `GET /api/fs/browse`. This is the only
   privileged capability the shell grants the page.
6. **Desktop toast notifications** when a question is raised and the window is not focused — this is
   the job orchestrator §10 explicitly assigns to the Electron shell ("desktop toasts … it is the
   Electron shell's job in ui, not ours"). Clicking the toast focuses the window on that question.
7. **External links** open in the system browser, never in-app.

That is the complete list. The shell owns **no** UI beyond the window chrome and the tray menu, **no**
business logic, **no** filesystem access on behalf of the page beyond the folder picker, and **no**
database or transcript access — foundation §5.3's rule ("through the API, never by reading files")
applies to the shell too, because the browser client cannot read files and the two must not diverge.

**Security posture**: `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, a preload
exposing exactly `{ isElectron: true, coreUrl, pickFolder(), notify(), setBadge() }`, and navigation
locked to the core's origin. The web build ships a stub with `isElectron: false`; every consumer
feature-detects (`if (bridge.pickFolder)`) rather than branching on delivery mode.

Deferred to post-v1 (foundation §7 already defers the packaging half): auto-update, code signing,
MSI/Squirrel, global hotkeys, multiple windows, deep OS integration.

## 2. Information architecture

### 2.1 Screens and routes

| Route | Screen | Purpose |
|---|---|---|
| `/` | **Board** | The roster as a board of agent cards. The home screen and the drag surface. |
| `/agents/:id` | Agent detail / editor | Definition, persona, permissions, integrations, skills, diagnostics, session history. |
| `/agents/new` | Agent wizard | Draft-from-description → edit → save (§6). |
| `/projects` | **Projects** | The project list: status, health, and the agent→project drop target (§5.1). |
| `/projects/:id` | Project page | Activity timeline, work items, workspaces ("review needed"), defaults, health. |
| `/sessions` | **Sessions** | Every session, newest first, filtered by status — the run history (§9.5). |
| `/sessions/:id` | Session view | Live transcript, controls, usage (§9). |
| `/assignments` | **Assignments** | Open and closed assignments with their seats, phase and token budget (§10.5). |
| `/assignments/:id` | Assignment view | The pair conversation, phase, rounds, budget (§10). |
| `/questions` | **Question inbox** | Every card the user must answer (§11). |
| `/questions/:id` | One card, focused | The ntfy deep-link target. |
| `/usage` | Usage | Plan-window local estimate, queue, per-assignment spend (§12). |
| `/settings` | Settings | Remote access, capacity, notifications, logs, health, about (§13). |

Thirteen routes. Every one is deep-linkable and survives a reload, because the ntfy notification and
the Electron toast both navigate by URL.

**Sessions and assignments are destinations, not just detail routes.** Both started with a `:id` route
and no index, which meant a session that had stopped, and the assignment it belonged to, could only be
found again by walking back through a project page's activity timeline. A record with no index is a
record the user cannot look up, and the session history is exactly what someone reaches for after a
run ends.

### 2.2 Navigation

**Desktop (≥ 900px)**: a narrow left rail — Board · Projects · Sessions · Assignments · Questions
(badge) · Usage · Settings — plus a persistent top bar carrying the connection indicator, the global
search-free "New agent" and "Add project" buttons, and the theme toggle. Detail screens open as full
pages, not modals, so they can be linked and shared.

**Phone / narrow (< 640px)**: a bottom tab bar with the same seven destinations (thumb-reachable, 48px
targets), the top bar collapsed to a title and a single overflow menu. Detail screens push; modals
become **bottom sheets**.

**The shell owns the scroll, the document does not.** The top bar and the rail are fixed to the
viewport and the content region is the scrollport. A page that scrolls as one document takes the
navigation with it, and on a long session view it takes the run's own controls too — which is the one
case where the user is reaching for Stop *because* the page is long. Every screen's sticky element is
therefore sticky inside the content region rather than inside the window.

**Tablet (640–900px)**: the desktop rail collapses to icons.

The badge on Questions comes from `GET /api/orchestrator/status` (`questions.open`) and is kept live
by `assignment.question.raised` / `.answered`. It is mirrored into the Electron tray and taskbar badge
(§1.5).

### 2.3 One layout, three viewports

D3 says one frontend for Electron and the tailnet browser. The layout is responsive from a single
component tree; the screens where the difference is more than reflow are called out explicitly:

| Screen | What actually changes on a phone |
|---|---|
| **Board** (§5) | Drag is not the primary path. Cards get an explicit **Launch** button and a `⋯` menu; reorder moves into an explicit "Reorder" mode with move-up/move-down controls. |
| **Projects** (§5.1) | The card grid collapses to one column. There is no drag at all, so every card's **Launch an agent…** carries the whole gesture. |
| **Session view** (§9) | The right-hand usage rail collapses under the header; tool blocks default collapsed; steer input docks above the keyboard. |
| **Assignment view** (§10) | The two-seat side-by-side conversation stacks into one column, seat identity carried by the avatar+name row rather than by column position. |
| **Question inbox** (§11) | Identical by design — this is the phone's primary surface and must not be a reduced mode (remote §12.8). Option buttons are full-width. |
| **Settings → Remote** (§13) | Token creation and the QR are **local-only** by remote's deny list; the phone sees them disabled with the reason, and sees its own pairing state instead. |
| **Project quick-add** (§7) | The native-dialog Browse button is replaced by the `/api/fs/browse` navigator. Both viewports always accept a typed path. |

## 3. Data and transport

### 3.1 The API client

One thin `fetch` wrapper. Its entire responsibility:

- prefix `/api`, JSON in/out, `Cache-Control: no-store` respected;
- attach `Authorization: Bearer <token>` **when a token is held** — in Electron and at `127.0.0.1`
  there is none, because foundation §6.4 pins that the local listener has no authentication and that
  this is the intended trust boundary;
- map remote's status codes (remote §8.2, §12.3) onto typed results, because they are semantically
  distinct and the UI must not treat them as generic failures:

| Code | Meaning | Client behaviour |
|---|---|---|
| `401` | absent/invalid/expired/revoked token | clear the stored token, show the pairing screen, **never retry** |
| `403 route_denied_remotely` | remote deny list | render as "not available remotely", **never retry**, never as a network error |
| `409 remote_access_required` | no per-agent grant | show the grant prompt, then **retry the original request** (§6) |
| `429` | auth lockout or route bucket | honour `Retry-After`, show a countdown |
| `503 remote_unavailable` | listener in `waiting` | only reachable locally; show the Tailscale state from `/api/remote/status` |

Everything else surfaces the server's message verbatim. Backend messages are written for humans
(runner §3.2: "never a stack trace to the UI") and the UI does not paraphrase them.

**Two GET requests cannot carry a header**, and both matter:

- **Avatars.** `<img src="/api/roster/agents/:id/avatar">` cannot set `Authorization`, so over the
  tailnet it would 401. The UI therefore fetches avatars with the API client and renders them from an
  object URL, memoised per agent id and revoked on eviction. No backend change is needed and none is
  requested.
- **`GET /api/logs/download`.** Same treatment: fetch → `Blob` → a synthetic anchor click.

### 3.2 Authentication and pairing (browser mode only)

Per remote §12.1:

1. The desktop settings screen creates a token (local-only) and renders the returned `qrUrl`
   (`<client URL>/#t=<token>`, where the client URL is `http://<magicdns>:7478` when the phone
   reaches the listener directly and `remote.publicUrl` when a proxy fronts it) as a QR **and** as
   copyable text. The screen never assembles that URL itself — only the core knows which it is.
2. The phone opens that URL. On boot the client reads `location.hash`, extracts `t=`, stores it in
   `localStorage` under one key with the server-returned label, and immediately calls
   `history.replaceState` to strip the fragment — before the first render, so it cannot be
   screenshotted from the address bar.
3. Manual paste is always available on the pairing screen.
4. A token within 14 days of `expiresAt` raises a persistent, dismissible banner (remote §4.4) — a
   credential that expires silently while you are away is worse than one that does not expire.

The pairing screen is reached only by a `401`. It is never shown in Electron or at loopback.

### 3.3 The event stream

**Two websockets at most, and only one of them is always open.**

| Connection | When | Carries |
|---|---|---|
| `/api/events` | always, from app boot | lifecycle, questions, assignments, projects, roster, remote grants, diagnostics |
| `/api/sessions/:id/stream` | only while a session view is open | `session.delta`, `session.message`, `session.tool.*`, `session.usage` for that one session |
| `/api/logs/stream` | only while the log screen is open | log records |

The global feed exists so the board, the badge, and the inbox stay live everywhere. The per-session
feed exists so a phone watching one session does not receive token deltas for every other running
session. Foundation's `/api/events` takes an optional **`types=`** filter (§6.5, closing §19's R4) — exact
event types or `prefix.*` patterns, applied identically to the live fan-out and to the `since=`
replay — so the global feed subscribes to lifecycle, question, assignment, project, roster and remote
types and is never sent another session's `session.delta`/`session.message`/`session.tool.*`/
`session.usage` at all. Per-session detail rides its own socket. Nothing is discarded client-side, and
the reconnect replay returns the same subset the socket was streaming.

**Authentication of the stream** is remote §3.4's ticket dance, and it is entirely inside the
`EventStream` singleton: `POST /api/remote/stream-ticket` → open `?ticket=…` → discard the ticket.
Locally there is no ticket and the socket opens directly. Screens never know which happened.

**Reconnection is replay, not reload** (remote §12.10). The client persists an `/api/events`
watermark (last event id) in `localStorage`. On reconnect it replays `/api/events?since=<watermark>`,
then resumes the live stream. Session content additionally resumes from the last **transcript byte
offset** (§9.4). A tailnet drop must not cost the user their place and must not trigger a full
refetch.

**The persist/replay split is honoured exactly as runner §15.2 #12 pins it.** `session.delta`,
`session.message`, `session.tool.*` and `session.usage` are **not** persisted and **not replayable**;
their durable record is the transcript. So the reconnect path is: replay persisted events (lifecycle,
questions, diagnostics) **and** tail the transcript from the stored byte offset. Anything the UI
renders from a non-persisted event must also be derivable from a transcript line, or it is a bug.

**Connection state** is a first-class UI object with three values — `live`, `reconnecting`,
`offline` — rendered as a single dot in the top bar with a tooltip, and as a full-width banner when
`offline` for more than five seconds. Controls are **not** disabled while reconnecting; requests are
attempted and their failures reported, because every runner control verb is idempotent (runner §11.1)
and a retry that the UI refuses to send is worse than one the server absorbs.

### 3.4 Invalidation map

The `EventStream` maps event types to cache operations. The interesting entries:

| Event | Effect |
|---|---|
| `roster.changed` | refetch the roster list (covers external file edits and `git pull`) |
| `session.queued/started/paused/resumed/ended/orphaned` | patch the session record, invalidate the fleet status and the project timeline |
| `session.delta/message/tool.*/usage` | append to the per-session ring buffer only (never the query cache) |
| `runner.queue.changed`, `runner.ratelimited` | patch the queue panel |
| `assignment.question.raised/answered` | invalidate the inbox, bump/clear the badge, fire the Electron toast |
| `assignment.turn.*`, `assignment.round.completed`, `assignment.halted`, `assignment.closed` | invalidate the conversation and the assignment header |
| `project.clone.progress/completed/failed` | patch the clone progress row |
| `workspace.acquired/released/orphaned`, `project.scope.overlap` | invalidate project health |
| `remote.agent.access.granted/revoked/expired` | patch the card's remote badge live (remote §12.4) |
| `remote.auth.failed` | surface a settings-level warning |

### 3.5 Feature detection

The UI learns what exists from **`GET /api/config/effective`** (edition, `policy.allowPermissionElevation`,
`orchestrator.notify.enabled`, runner defaults) and **`GET /api/health`** (module list, degraded
secret provider, the `ANTHROPIC_API_KEY` warning) at boot, and never by probing for a 404
(remote §12.6). Both are refetched on reconnect. A missing `orchestrator` module is a first-class
degraded state, not a crash: there is no launch path at all without it (runner §14 D9), so the board
renders with launch disabled and one explanatory banner.

## 4. What the UI never does

Stated once, because every screen below inherits it:

- It never reads the filesystem, the SQLite database, or a transcript file. Logs come from
  `/api/logs*` (foundation §5.3); transcripts from `/api/sessions/:id/transcript`.
- It never composes permissions. The effective set comes from `POST /api/roster/agents/:id/validate`
  (roster §9.1). Roster is the sole composer (roster §6.2).
- It never derives `disagreement`, `contested`, assignment `outcome`, project `health`, or the fleet
  `state` vocabulary — all are server-computed.
- It never shows a plan-window percentage or a "remaining quota" (runner §7.4, §15.2 #13).
- It never presents a dollar figure as spend (runner §7.3).
- It never offers a default-on-timeout action for an approval gate (orchestrator §16.4).
- It never invents question options; it renders `options_json` as given.

## 5. The roster board

The home screen and the element's centre of gravity.

### 5.1 Layout

Desktop: a responsive grid of agent cards (min 260px, 3–5 columns), full width. Above the grid:
filter chips (specialty, "working now", "needs attention", archived) and a sort control that defaults
to **board order**.

Projects used to ride along here as a 220px rail pinned right. They are their own destination now —
**`/projects`** (§2.1), a full-width grid of the same project cards with "Add project" above it. The
board answers "who do I have"; `/projects` answers "what am I pointed at". What each agent is
*currently* working on still rides on its own card, which is the half of the rail's job the board
actually needed.

The projects screen keeps everything the rail was load-bearing for. It is still the drop target set
(§5.3), which is why it carries the same compact strip of draggable agent chips the project page uses
for its work-item rows (§8.2): a drop target with no drag source on the same screen is not a feature.
It still reads `status` and `health` from the server and never recomputes them, and it still offers
each card's **Launch an agent…** as §5.4's pointer-free equivalent.

### 5.2 Card anatomy

```
┌──────────────────────────────────────┐
│  🐛   Priya                    ⋯     │   avatar · name · menu
│       bug-patching                   │   specialty chip (colour + word)
│  "Reproduces first, then fixes."     │   tagline, one line, truncated
│  ────────────────────────────────    │
│  ● working · littlepocketmuseum      │   status pill + where
│  Reproducing the 500 on /invoices    │   headline from fleet status
│  ─────────────────────────────       │
│  🔑 needs credential   📱 remote 2d  │   badges
└──────────────────────────────────────┘
```

| Element | Source |
|---|---|
| Avatar | `agent.avatar` — `emoji` (rendered at 28px in the system emoji font), `initials` + `color`, or `file` via the object-URL fetch of §3.1. Roster guarantees one of the three is always present, so there is no missing-image case. |
| Name, specialty, tagline, tags | `agent.json` fields (roster §3) |
| Status pill | `GET /api/orchestrator/status` → `idle \| queued \| working \| awaiting_user \| paused \| halted` (orchestrator §16.6), **verbatim vocabulary**, rendered as a coloured dot **plus the word**. That endpoint is orchestrator M9, later than ui M2, so the board's first cut derives the same vocabulary from `session.*` events and swaps to the endpoint when it lands — the pill's rendering and its words never change, only where the value comes from (IMPLEMENTATION M2). |
| Headline + since | fleet status `headline` / `since`; before orchestrator M9, the session's `summary` and `started_at` stand in |
| Live indicator | the `working` dot pulses gently (2s, `prefers-reduced-motion` disables it); a thin progress line animates while `session.delta` is arriving for that agent |
| Overseer mark | `capabilities.overseer` — a small chevron beside the name |
| "needs credential" | any integration whose API projection reports `resolved: false` (roster §10) |
| "diagnostic" | a `RosterDiagnostic` on the agent (roster §2.3) — invalid file, unknown model, missing skill |
| Remote badge | home edition only: `GET /api/remote/agents` grant with its `expiresAt` rendered as "2d left" (remote §12.4), live from `remote.agent.access.*` |
| Pinned | a pin glyph; pinned agents sort ahead of the rest |

The card body is a link to `/agents/:id`. The `⋯` menu carries every action that has a drag
equivalent, plus the ones that do not: **Launch on…**, **Start a pair…**, **Duplicate**, **Edit**,
**Export**, **Pin**, **Allow remote starts** (home edition), **Archive**.

An **archived** agent is hidden behind the archive filter and renders greyed with actions reduced to
Restore/Export — it must remain visible because sessions reference it (foundation §1.4). A session
whose `agent_id` no longer resolves renders as "deleted agent" wherever it appears, per the same rule.

### 5.3 Drag and drop, precisely

**Library**: `dnd-kit` with `PointerSensor`, `TouchSensor` (250ms long-press activation, 5px
tolerance) and `KeyboardSensor`. HTML5 native drag-and-drop is **not** used: it does not fire on
touch, cannot be driven from the keyboard, and cannot render a custom drag preview reliably.

**One `DndContext`** wraps each drag surface — the board, the projects screen, a project page. The
draggable payload is
`{ type: 'agent', agentId }`; every droppable declares `{ type, … }` and the drop handler dispatches
on it.

| Drop target | Payload | What happens |
|---|---|---|
| **Project card** on `/projects`, or the project header on `/projects/:id` | `{ type: 'project', projectId }` | Opens the **launch flow** (§6) pre-filled with agent × project. Nothing is started by the drop itself. |
| **Work item row** on a project page | `{ type: 'workItem', workItemId, projectId }` | Launch flow pre-filled with agent × project, the item attached (`workItemIds`), its `title` seeded into the prompt and its `scopePaths` shown as a scope hint. |
| **Another agent card** | `{ type: 'agent', agentId }` | Opens the **pair create dialog** (§10.4) with the dragged agent in the drafting seat and the target in the critic seat. Lands with the assignment view (M9); until then the target is inert. |
| **The board grid itself** | sortable context | **Reorder.** Optimistic local reorder, then persist. |

**Reorder persistence** uses roster's `agent_ui_state.board_order` (roster §2.2), written through
**`PUT /api/roster/board-order { order: string[] }`** (roster §9.5, closing §19's R2) — a whole-list,
idempotent, single-transaction rewrite, which is why the client sends the entire ordered id list
rather than a per-card patch. It applies optimistically and rolls back with a toast on failure; an id
the roster does not know is a 400 and the previous order stands.

**During a drag**: the source card lifts (shadow + 2° tilt, ≤150ms), valid targets outline in the
accent colour, invalid ones dim, a long list auto-scrolls near its edges, and a floating label reads
*"Launch **Priya** on **littlepocketmuseum**"*. `Esc` cancels. Drop on nothing cancels silently.

A project that cannot be launched against — `provisioning`, `archived`, or health `missing` (projects
§2.2, §2.3) — is **not** a valid target: it dims during the drag and its tooltip says why. Refusing at
the drop is better than a launch flow that fails on submit.

### 5.4 Every drag has a non-drag equivalent

This is a hard requirement — the phone browser has no drag, and keyboard users must not be second
class.

| Gesture | Keyboard | Pointer-free / touch |
|---|---|---|
| Agent → project | Tab to the card, `Space` to lift, arrows to move between targets (dnd-kit announces each target in a live region), `Space` to drop | Card `⋯` → **Launch on…** → project picker → launch flow. Also: project page → **Launch an agent…** → agent picker. |
| Agent → work item | as above | Work item row `⋯` → **Assign an agent…** |
| Agent → agent (pair) | as above | Card `⋯` → **Start a pair…** |
| Board reorder | `Space` to lift, arrows, `Space` to drop | **Reorder mode** toggle above the board: each card gains ▲▼ buttons and a position readout; leaving the mode persists once. |

Both paths call the same code. There is no "mobile launch" and "desktop launch" — one launch flow,
reached three ways.

## 6. The launch flow

Agent × project × prompt, in under a minute. A centred dialog on desktop, a bottom sheet on phone.

```
Launch                                                    [×]
┌──────────────────────────────────────────────────────────┐
│  🐛 Priya  ▾            on   📁 littlepocketmuseum  ▾     │
│                                                          │
│  ┌────────────────────────────────────────────────────┐  │
│  │ What should Priya do?                              │  │   ← autofocused
│  │                                                    │  │
│  └────────────────────────────────────────────────────┘  │
│                                                          │
│  ▸ Details          implementer · write · no work items  │   ← collapsed
│  ▸ Permissions      acceptEdits · 12 allow · 4 deny      │   ← collapsed
│  ☐ Allow remote starts for Priya            (home only)  │
│                                                          │
│                              [ Cancel ]   [ Launch ⏎ ]   │
└──────────────────────────────────────────────────────────┘
```

**The fast path is: drop, type, Enter.** Everything else is collapsed and pre-filled.

**Pre-fill rules.** Agent and project come from the drag. When the flow is opened from a project with
`defaults.agentIds`, `agentIds[0]` is pre-selected (projects §1.2). Role defaults to `implementer`
where the agent declares it, else `capabilities.roles[0]` — the same rule orchestrator applies
server-side (§2.3), stated in the UI only so the collapsed summary is honest.

**Details** (collapsed): role picker — **every** role, with the agent's declared ones marked;
choosing another is allowed and the create call returns a `role_not_declared` warning saying the
agent works the seat without that role's addendum (owner decision 2026-08-18, orchestrator §9-5) —
write toggle,
work-item multi-select from the project's `open` items, and — when the project has open assignments —
the scope-overlap warning surfaced ahead of submit rather than after.

**Permissions preview** (collapsed) calls `POST /api/roster/agents/:id/validate` with the project id
and renders the compiled effective set: mode, allow, deny, ask, and diagnostics. Two things are never
collapsed:

- **Elevation.** If the project declares `defaults.permissionElevation`, a bordered banner shows the
  widened rules **and the mandatory reason string** (projects §1.2, roster §6.2). Invisible privilege
  escalation is the failure mode this exists to prevent, so it is shown before launch and again in the
  session header.
- **Elevation refused by policy.** When `policy.allowPermissionElevation` is false — the work edition
  — the same banner renders **disabled** with "not permitted on this machine (work edition)". Shown
  disabled with a reason, not hidden.

The preview is advisory-honest: it is a dry-run compile against agent × project, and the assignment
layer for a solo launch is whole-project scope, so what it shows is what will apply. Where an
assignment narrows further (a pattern launch, §10.4), the dialog says so.

**Remote access toggle** (home edition only). At the desk it pre-authorises the agent by calling
`PUT /api/remote/agents/:id/access`, and shows the resulting `expiresAt`. From the tailnet it is
pre-checked and rides the launch as `confirmRemoteAccess: true`, granting and starting in one call
(remote §6.3).

**Submit** calls `POST /api/assignments/solo { projectId, agentId, prompt, role?, write?, workItemIds? }`
— orchestrator mints the trivial assignment and starts the first session, returning
`{ assignmentId, sessionId }` (orchestrator §16.7). The UI navigates straight to `/sessions/:id`. There
is no second code path for "one agent" versus "a collaboration".

**Failure handling.** `429 queue_full` renders as "the queue is full (50) — stop or wait for something
to finish", with a link to the queue panel. A `409 remote_access_required` is **not an error**
(remote §12.5): the sheet swaps to *"Allow **Priya** to be started remotely?"*, one tap grants, and the
original request is retried automatically.

## 7. Agent wizard, editor, and duplicate-and-edit

### 7.1 The wizard

Three steps, and the whole thing must fit inside a minute.

**Step 1 — Describe.** One textarea, autofocused, with a real placeholder ("Someone who watches our
PHP sites for 500s and patches them, but always writes a failing test first"). Optional inline hints:
name, model tier (`fast | balanced | max`), a project to look at, "this one coordinates others"
(overseer). Submit calls `POST /api/roster/draft` (roster §12.1).

**Step 2 — Drafting.** A short animated wait with the description echoed. Drafting is one inert
Sonnet call and is expected to be seconds (roster §12.2); past 20s an inline "still working" note
appears, past 60s a cancel.

**Step 3 — Review and edit.** The returned draft rendered as an editable form, with roster's
**per-field-group `rationale` shown beside each section** — the thing that makes the wizard feel like
a collaborator rather than a slot machine:

| Section | Editing |
|---|---|
| Identity | name, emoji avatar (picker), tagline, specialty (the closed enum, roster §3.1), tags |
| Persona | a plain markdown textarea holding `persona` verbatim; the `replace` mode carries the warning roster requires ("this agent will not receive Claude Code's coding guidance") |
| Model | alias picker (`opus`/`sonnet`/`haiku` + `default`/`best`), optional fallback and effort; a full id is typeable |
| Permissions | three rule lists (allow/deny/ask) with add/remove, mode picker, and a plain-language note that deny wins and allow is only auto-approval |
| Roles | checkboxes over the pinned five — which seats this agent may be given |
| Role addenda | one markdown textarea per role, holding `roles/<role>.md` verbatim (roster §4) — how it behaves *once it is in* a seat. Not tied to the checkboxes above: a role may carry an addendum without being listed, and vice versa, so every box is always shown and an unlisted one is labelled as such. Emptying a box deletes the file. Drafting never fills these in |
| Suggested skills | checkboxes; accepting one creates the stub `SKILL.md` on save (roster §12.4). Bodies are not authored here. |
| Suggested integrations | listed read-only with their `secretRef` placeholders and a "you will need to supply this credential" note; wiring an MCP server is the editor's job, not the wizard's |

`warnings[]` render as a dismissible list at the top. `degraded: true` renders a plain "Claude couldn't
finish this draft — here's what it produced; fill in the rest" banner and keeps every partial field
editable, exactly as roster's graceful-degradation contract intends.

**Redraft** re-calls `/draft` with the original description plus the current edits as context, and
presents the fresh draft **beside** the current one for an explicit swap — never a silent overwrite
(roster §12.4).

**Save** is an ordinary `POST /api/roster/agents` with `meta.origin: "drafted"`. The user's edits
always win; there is no merge. The new card appears on the board (via `roster.changed`) with a brief
highlight, and the board scrolls to it.

### 7.2 Duplicate-and-edit — a first-class path

Card `⋯` → **Duplicate** calls `POST /api/roster/agents/:id/duplicate { name? }` and opens the
returned definition **directly in step 3's editor**. Because roster's drafting is stateless, "draft →
tweak → save" and "duplicate → tweak → save" are literally the same component; that is the reason
roster designed it that way (roster §15, decision 8) and the UI honours it rather than building two
forms.

The editor shows a small "cloned from **Priya**" line (`meta.duplicatedFrom`) and a note that
integrations point at the **same credentials** — true per roster §9.2, and a surprise if unstated.

### 7.3 The agent detail page

The same editor plus: session history for that agent (filtered `GET /api/sessions?agentId=`),
diagnostics, the effective-permissions preview against a chosen project, the remote grant with its
expiry, and Archive/Export. Archive is a confirm dialog naming what is retained ("history and
transcripts are kept; the id is never reused"); hard purge is offered only when roster reports it is
possible (no sessions reference the agent) and is a typed confirmation.

**Avatar upload is not in v1 — by choice, not for want of an API.** Roster ships
`PUT /api/roster/agents/:id/avatar` (roster §9.5, closing §19's R7): multipart, size- and type-capped,
written into the agent folder as `avatar.png` with `agent.json` flipped to `kind: 'file'` in the same
operation, and `DELETE` reverting it. The *UI* for it stays deferred (§20) — the wizard produces an
emoji, the editor offers emoji or initials+colour, and a PNG dropped into the agent folder by hand is
honoured on the next `roster.changed`. When the upload UI is wanted, the endpoint is already there.

## 8. Project quick-add and the project page

### 8.1 Quick-add — two routes, one dialog, under a minute

A single dialog with two tabs, both of which are **inspect → confirm**, never a form to fill:

**Folder.** Electron shows a **Browse** button wired to the native dialog (projects §2.1); the browser
shows a breadcrumb navigator over `GET /api/fs/browse?path=` restricted to the configured browse
roots. Both always accept a typed absolute path. On selection the dialog calls
`POST /api/projects/inspect { localPath }` and fills name, slug, git remote, default branch, and
renders projects' warnings verbatim (network share, uncommitted changes, empty folder). **Create**
posts the reviewed values. Refusals (nested project, already registered, inside the data root) render
as the server's message with the offending path.

**Clone URL.** Paste a URL → `POST /api/projects/inspect { repoUrl }` → proposed target path and
name → **Clone** calls `POST /api/projects/clone` and returns immediately. The dialog can be
dismissed: the project appears on `/projects` at once with a `provisioning` state and an inline progress
bar driven by `project.clone.progress`, flipping to `active` on `completed` or disappearing with the
git stderr shown verbatim on `failed` (projects §2.2). Auth failures show git's own message — the
credential helper is the user's, and paraphrasing it would hide the fix.

The browser path works identically over the tailnet (remote §3.3 deliberately allows `fs/browse`), so
project registration is never stranded on the desktop.

### 8.2 The project page

Four regions, in priority order:

1. **Header** — name, path, branch, vcs, `status`, health chips derived server-side (`missing`,
   `dirty`, `stale-agents`, `orphaned-worktrees`), and a **Launch an agent…** button (the non-drag
   equivalent of dropping onto the project). A `missing` path offers **Relocate**.
2. **"Review needed"** — the workspaces list from `GET /api/projects/:id/workspaces`. A worktree
   retained because it has commits or uncommitted changes is the loudest thing on the page: branch
   name, commit count, dirty flag, and a **Clean up** action behind a confirm. Projects never discards
   agent output (§4.4), so the UI never makes cleanup one click.
3. **Activity timeline** — `GET /api/projects/:id/activity`, grouped by assignment, newest first. Each
   row: the agents' avatars, pattern, outcome chip (`running`/`completed`/`stopped`/`failed` — read,
   never derived), scope summary, workspace kind/branch, token totals, and the per-session list with
   status, summary, a transcript link, a pin toggle, and a "started remotely" badge where
   `origin === 'remote'` (remote §12.9). A session whose transcript was pruned says
   "transcript pruned" rather than offering a dead link.
4. **Work items** — a simple ranked list per status, inline-creatable (title only is enough), drag-
   reorderable with the same ▲▼ fallback, and each row a drop target for an agent (§5.3). Deliberately
   thin: no priorities, labels, or assignees, matching projects §7.2.

**Settings** (collapsed): default agents (ordered), permission override, permission elevation with its
required reason, env entries (secret refs shown as `secretRef` names with a set/unset indicator, never
values), setup command, instructions path, workspace policy, retention overrides.

## 9. The session view

### 9.1 Decision: structured event rendering, not a terminal emulator

**xterm.js is not used.** The reasoning is not aesthetic:

- **There is no terminal stream to emulate.** Runner emits *structured* events (`session.message`,
  `session.tool.start/end`, `session.delta`, `session.usage`, `session.question.*`) and writes
  *structured* JSONL transcript lines (runner §8.1). No element produces a PTY, a control sequence
  stream, or a cursor. Adopting xterm.js would mean **inventing** a text serialisation of structured
  data and then parsing it back — strictly worse than rendering the structure.
- **The structure is the product.** Collapsible tool calls, a linked artifact path, a question rendered
  as the card that was actually answered, a diff-aware Edit block, a pinned "elevated permissions"
  banner — none of that survives flattening to a scrollback buffer.
- **It would break the phone.** A fixed-column terminal is the single worst thing to read on a 390px
  viewport; structured blocks reflow.
- **It costs ~250KB for the privilege.**

**The one narrow exception**: `Bash` tool *results* can legitimately contain ANSI colour codes, because
they are captured program output. Those are rendered inside a monospace `<pre>` by a ~2KB
ANSI-SGR-to-`<span>` converter that handles colour and bold and **discards** cursor movement,
alternate screens and everything else. That is a formatter, not a terminal, and it is scoped to one
block type.

### 9.2 Anatomy

**Header, controls and steer field are pinned together** to the top of the content region, not just
the header. Scrolling a long transcript must not take Stop, Pause and the steer field with it: those
are the controls the user reaches for *because* the run is long. The notices below them (elevation,
diagnostics, pruned transcript) scroll with the body — they are read once, not operated.

**Header** (pinned): agent avatar + name, project, a link to the assignment, status pill (runner's
vocabulary verbatim: `queued | running | paused | done | failed | interrupted | orphaned`), model,
permission mode, workspace kind + branch, and the badges that must never be missed —
**elevated permissions (with the reason)**, **started remotely**, **question bridge disabled** (from
`session.started`'s `questionBridge: 'disabled'`, runner §5.6), **MCP server needs auth**, and any
`session.diagnostic`.

**Body**: an ordered list of blocks keyed by `seq`.

| Block | Rendering |
|---|---|
| Prompt | the initial prompt, each steer (marked "steered", and "interrupted the turn" when it did), and each injected answer message, visually distinct from assistant text |
| Assistant text | sanitised markdown; while streaming, `session.delta` appends into a pending block with a caret |
| Tool call | one collapsed line — icon, tool name, and a one-line input preview (`Edit  src/invoices.php`) — expanding to full input and result. `Bash` gets the §9.1 `<pre>`; `Edit`/`Write` get a compact diff view; `Read`/`Glob`/`Grep` get a count summary; `mcp__agentmanager__*` calls render as named orchestration actions ("reported status: *Draft complete*") because that is what they are. Errors expand by default. |
| Question | the card as it was asked, with the answer, who answered it (`answered_via`), the latency, and whether it landed **inline** or **after a park** — the delivery distinction runner tracks (§10) and the user will otherwise not understand |
| Diagnostic / error | severity-coloured, always expanded, carrying the server's message |
| End | status, exit reason (runner's closed vocabulary, rendered as a sentence), turns, duration, totals, and the summary |

Rendering is capped at the most recent 500 blocks with a **Load earlier** control; there is no
virtualisation library in v1 (a cap is simpler and the transcript is paged anyway).

**A message with no text of its own is not a block.** An assistant message whose content is only
`tool_use` parts, and a user message whose content is only `tool_result` parts, carry no prose —
runner emits `session.message` for both anyway, because the `session.tool.*` events that follow
number their `seq` from it (runner §10). The tool block *is* the rendering of that exchange, so the
message beside it is dropped. Rendering it produces an empty card beside every tool call, and the live
stream and the replayed transcript disagree about the transcript's shape — the replay never built
those blocks, which is why **Load earlier** appeared to repair the view.

**Nothing widens the column.** The transcript column can shrink below its content's intrinsic width;
a long command line or tool preview wraps, ellipsises or scrolls inside its own block. A block that
sets the page's width pushes the whole layout — including the usage rail — off the right edge.

**Usage rail** (right on desktop, collapsed under the header on phone): live input/output tokens from
`session.usage`, the assignment budget bar in **tokens** (`tokens_used / token_budget`, orchestrator
§16.8), and — labelled exactly — **"estimated model cost"** for `session_usage.cost_usd`, with a
tooltip stating it is a client-side estimate from a bundled price table and not a charge (runner §7.3,
§15.2 #13). It is never summed into anything that reads like an invoice.

### 9.3 Controls

Mapped one-to-one onto runner §11.1, all idempotent, all identical over the tailnet:

| Control | Call | Shown when |
|---|---|---|
| **Steer** | `POST /api/sessions/:id/steer { text, interrupt }` — a text field with an "interrupt the current turn" toggle, defaulting off. The field is a form: **Enter submits it**, and a Send button beside it does the same thing. A text field whose obvious gesture does nothing is a field the user types into twice. | `running` |
| **Pause** | `POST …/pause` | `running` |
| **Resume** | `POST …/resume` | `paused` |
| **Stop** | `POST …/stop` | `queued`, `running`, `paused` |
| **Continue** | `POST …/continue` with a prompt — the answer to runner §5.5's "the agent asked in prose and stopped" case | `done`, `failed`, `interrupted` |
| **Relaunch** | a fresh launch flow, pre-filled | `orphaned` where resume is impossible (no `sdk_session_id`, or the workspace is gone) |
| **Pin** | `POST …/pin` | always — the retention exemption, labelled "keep this transcript" |

A control that does not apply is **shown disabled with the reason**, not hidden — "paused sessions
can't be steered; resume first". A `paused` session whose `exit_reason` is `awaiting_answer` shows
**the card itself**, answerable in place, and **no Resume button**, because runner auto-resumes on the
answer and a second resumer is the bug runner §15.1 #7 warns about.

**Open cards are answered here, not only in the inbox.** §11.3 pins one answer endpoint and one card
shape "local and remote alike"; the same rule says a card is answered where it is *seen*. A run that
stopped to ask is looked at on this screen, so the screen reads its assignment's open cards
(`GET /api/questions?status=open&assignmentId=…`, narrowed to this session by the projection's
denormalised `sessionId`) and renders the **same component and the same answer hook** the inbox uses.
A second implementation is how the two would drift; the link to the inbox remains for the cards this
session did not raise.

### 9.5 The sessions index

`/sessions` lists every session, newest first, filtered by runner's status vocabulary with an **All**
tab. One request per tab (`GET /api/sessions?status=`), the server's order preserved, and no join: the
row's project and assignment ids come denormalised on the record and the roster is read only for the
name and avatar behind an `agentId`. A session whose agent has since been deleted still renders — the
transcript is the record, not the roster entry — and a pruned transcript says so on the row rather
than at the end of a click.

### 9.4 Live streaming, replay, and the byte-offset contract

Opening a session view:

1. `GET /api/sessions/:id` → record, status, `transcript_bytes`, resume affordances.
2. `GET /api/sessions/:id/transcript?tail=<bytes>` → the last whole JSONL lines plus `from` / `next`
   offsets; **Load earlier** then walks backwards, and `?from=<offset>&limit=…` pages forward from any
   retained offset. Both forms return whole lines only and the offsets to resume from.
3. If `running`, open `/api/sessions/:id/stream`.

**`seq` is the join key.** Transcript lines carry `{seq, ts, type, …}` (runner §8.1) and every session
event payload carries `seq` (runner §10), so replayed history and live events merge into one ordered
list with duplicates collapsed by `seq`. This is what makes step 2 and step 3 overlapping rather than
racing.

On disconnect the client keeps the last `seq` and the last byte offset. On reconnect it replays
`/api/events?since=` for lifecycle changes and re-tails `transcript?from=<offset>` for content — never
a full refetch (remote §12.10). A pruned transcript returns the defined pruned result and renders as
"transcript pruned" (runner §15.2 #11).

Opening a **long, finished** session uses `GET /api/sessions/:id/transcript?tail=<bytes>` (runner
§11.1, closing §19's R6) — the last N bytes snapped forward to a line boundary, one request regardless
of transcript size, which is what step 2 actually issues on open before the view scrolls back with
`from=`. `tail` and `from` are mutually exclusive. The companion rule matters just as much: a `from`
computed from `sessions.transcript_bytes` that lands **mid-line advances to the next newline**, so an
offset taken mid-flush can never split a record. The 500-block cap keeps rendering bounded either way.

## 10. The assignment / collaboration view

Where "collaborations render as a readable conversation between the agents, not two disconnected
terminals" is actually delivered.

### 10.1 Source

`GET /api/assignments/:id/conversation` (orchestrator §11.2) — rounds → ordered entries of
`turn | message | question`. Plus `GET /api/assignments/:id` for the header. The UI performs no merge
of its own: the ordering is the server's.

### 10.2 Layout

**Header**: goal, pattern, **phase** (`planned | running | awaiting_user | halted | converged |
closed` — rendered as words with a matching colour), the two (or one) seats with avatar, agent name
and role, the artifact path as a link, the scope summary, and the workspace.

**Progress strip**: `Round 2 of 3` as discrete pips, and the **budget bar** in tokens
(`tokens_used / token_budget`) with the remaining count. Both are always visible, because the round
cap and the budget are the two things that decide when this stops, and orchestrator §16.8 pins
tokens — never money — as the unit.

**Body**: rounds as labelled sections, entries within them as a dialogue:

- **Turn** — a chat-style entry attributed by avatar + name + **seat** ("Sam · skeptic"), carrying the
  `report_status` headline as a bold lead, the verdict when present (**accept**/**revise** as a chip,
  with blocking issues as a severity-marked list and non-blocking ones collapsed), the bounded excerpt
  as markdown, linked artifacts, tokens, and a **View full session** link to `/sessions/:id`. Turn
  status is shown when it is not the happy path: `unstructured` renders as "finished without a
  structured report", `blocked` as "waiting on a decision", `failed`/`orphaned` with the exit reason.
- **Message** — an indented, quieter entry with `from → to`, kind, and body, and the **delivery**
  state rendered distinctly: `inlined`, `read`, or **`undelivered`** with an explicit "never seen by
  the recipient" label. Orchestrator §16.5 requires the distinction and it matters: "I sent it and
  they ignored me" and "I sent it and they never saw it" are different failures.
- **Question** — the inbox card inlined at the point it was asked, with its recommendations and its
  answer, so the conversation reads as a whole.

On desktop the two seats sit in two columns with turns alternating sides (the "readable dialogue"
shape); on phone they stack into one column and identity is carried by the avatar row. The column
layout is a visual affordance only — the order is always the server's order.

**Halted / awaiting_user** states render a banner naming the halt reason and linking to the card that
resolves it. **Converged** renders the completion summary with the artifact link.

**Actions**: Advance (`POST …/advance` — the manual kick after a halt), Close (with a reason), and
Edit budget / round cap (`PATCH /api/assignments/:id`, which accepts `tokenBudget`, `roundCap`, `goal`
only — members and pattern are immutable, so the UI offers no such control).

### 10.3 A solo assignment is not a special case

Orchestrator §16.7 pins it: a drag-and-drop launch produces a real assignment with one member and no
rounds. The same view renders it — one seat, no round strip, no convergence — and the session view
links to it. There is no second code path.

### 10.4 The pattern create dialog

Driven entirely by `GET /api/patterns` (orchestrator §16.9): seats, allowed roles per seat, defaults,
`preferredTier`. For each seat the picker lists **every** candidate the endpoint returns, in the order
it returns them — role-declaring agents first, each carrying `declaresRole` for the label, then the
available, then the least loaded (owner decision 2026-08-18: capabilities rank, they never gate, so
the dialog must not hide an agent the user is allowed to seat) — showing each one's **model tier** and
current open-assignment count. Goal, scope paths, artifact path (required for `pair`), round cap and
token budget carry the config defaults; an `overseer` assignment has **one** seat, its workers arrive
as the child assignments its lead creates, and its token budget has no default and must be entered.
Submitting shows the returned `warnings[]` (scope overlap, projected cost, inverted tiers,
`role_not_declared`, `lead_not_overseer`) **before** the assignment starts, and a returned `gate`
renders as "waiting for your approval" with a link to the card.

Dragging one agent card onto another opens this dialog pre-filled (§5.3) — the visual, direct path to
the app's headline feature.

### 10.5 The assignments index

`/assignments` lists Open and Closed assignments — one request per tab
(`GET /api/assignments?status=`), the server's order preserved. A row carries the goal, the phase as
**the word** (§10.2's table), the pattern, the seats in the server's member order, the round count and
the budget in **tokens** — the same `budgetLine` the assignment view uses, so no currency figure can
appear on one screen and not the other (orchestrator §16.8).

The assignment outlives the sessions under it, which is what makes this the durable handle on "what
was this fleet doing". Without it the unit of work was the one record in the app with no index.

## 11. The question inbox

One surface for everything an agent needs from the user. It is the screen most likely to be used on a
phone, and it is the screen with the strictest contract.

### 11.1 List

`GET /api/questions?status=open`, newest first, with an **Answered** tab for the recent record. Each
row is the full card — there is no list-then-detail dance, because an inbox that requires two taps per
question is an inbox that goes unanswered.

The badge count comes from `GET /api/orchestrator/status`, is updated live by
`assignment.question.raised` / `.answered`, and is mirrored to the Electron tray and taskbar.

Rendering a card needs the asking agents, the project and the assignment, and **orchestrator §11.1
pins the list projection** that carries them (§19, R5): each item returns `id, kind, status, prompt,
options, createdAt, expiresAt, assignmentId, projectId, sessionId, recommendations[]` (each with
`agentId, role, stance, strength, rationale`), `disagreement`, `contested`, `answeredVia` — the same
shape `GET /api/questions/:id` returns plus its answer record. So a cold phone load is **one request**
and the client joins nothing: no roster, project or assignment fetch stands between arriving at
`/questions` and drawing the first card.

### 11.2 Card anatomy

```
┌───────────────────────────────────────────────────────────┐
│  APPROVAL          littlepocketmuseum · billing migration │  kind chip + where
│  Store transcripts in the DB or on disk?                  │  prompt
│                                        asked 4 min ago    │
│  ─────────────────────────────────────────────────────    │
│  ⚠ The team disagrees                                     │  disagreement (server-computed)
│                                                           │
│  🧪 Sam · skeptic        BLOCKING   → On disk             │
│     "A 500MB transcript in SQLite blows the WAL…"         │
│  📐 Ada · architect      lean       → In SQLite           │
│     "One store is simpler to back up."                    │
│  ─────────────────────────────────────────────────────    │
│  [ On disk ]  [ In SQLite ]              expires in 20h   │
│  ┌─────────────────────────────────────────────────────┐  │
│  │ Or answer in your own words…                        │  │  (allowFreeText only)
│  └─────────────────────────────────────────────────────┘  │
└───────────────────────────────────────────────────────────┘
```

| Element | Rule |
|---|---|
| **Kind chip** | `question` / `approval_gate` / `budget_halt`, one inbox, three kinds (orchestrator §16.3) |
| **The call being gated** | `context.toolName` and `context.toolInput` (orchestrator §11.1), directly under the prompt: the tool name as a chip and a one-line summary of the input — the command, the path, the URL — with the whole input behind a disclosure. **"Allow the agent to use Bash?" is not a decision anyone can make**; the whole question is *which* Bash, and a card that withholds it is asking the user to approve something they cannot see. The input is the agent's own and therefore untrusted (§1.4): it goes into the DOM as text, in a container that scrolls itself (§15). |
| **Attribution** | every recommendation carries its `agentId` **and the role it held**; an engine-raised gate is attributed to **"AgentManager"**, never to an agent (orchestrator §16.2) |
| **Stance ladder** | `blocking | strong | lean | defer` rendered **as the word** — never a number, never a bar, never a percentage (orchestrator §16.1). `blocking` is uppercase and red-marked, `strong` bold, `lean` normal, `defer` muted. Colour is always secondary to the word. |
| **Order** | the server's order (strength rank, then seat order). The UI does not sort. |
| **Disagreement / contested** | server-computed flags; `disagreement` renders a divider, `contested` a stronger banner. Never derived client-side. |
| **Options** | rendered from `options_json` exactly as given, as full-width buttons; `multiSelect` becomes checkboxes with a Submit; `allowFreeText` adds a text field. The UI **never invents an option** and never adds a "do nothing" default. |
| **Always allow** | a tool gate may carry a third option, `allow-always` (runner §5.1, owner decision 2026-08-18). The button shows the **rule it would add**, from `context.durableRule` — "Always allow / adds `Bash(npm run:*)` to priya" — because a button naming no scope asks the user to approve what they cannot see, which is §11.2's argument about the gated call applied to the standing permission. Clicking it is **two calls in this order**: the ordinary answer POST with `optionIds: ['allow-always']`, then `POST /api/roster/agents/:id/permissions/allow` with `{ rule }`. The rule and the agent are the server's; the UI derives neither, and renders the option as an ordinary two-outcome button whenever the card offers it without them. On success the screen says *"Allowed, and remembered for `<agent>`: `<rule>` — applies from its next session. Manage in the agent editor."* On a roster failure it says the call ran and the remembering did not, with the server's own message — **never** that the rule was saved. Both lines sit above the list rather than on the card, because the card has left the Open tab by the time the second call lands. |
| **Expiry** | `expiresAt` as a countdown. There is **no** timeout-default affordance — expiry of an approval gate is a denial (orchestrator §16.4) and the UI must not imply otherwise. |
| **Answered state** | after answering, the card moves to Answered showing the choice, who answered, and `answered_via` (`local` / `remote`). |

`budget_halt` cards get one extra affordance: the assignment's token bar inline, so "raise by 50%" is
a decision made with the number visible. The options themselves still come from the server.

### 11.3 The answer flow

`POST /api/questions/:id/answer { optionIds?, text? }` — one endpoint, local and remote, `answered_via`
recorded server-side. On success the card is optimistically marked answered and the session it belongs
to is invalidated.

What the user is not told, but what the UI must get right: an answer inside runner's 15-minute hold
resolves the pending `canUseTool` **inline** and the agent never left the tool call; after the park it
triggers runner's auto-resume (runner §5.3, §5.4). Both are the same POST. The **session view** shows
which happened; the inbox does not need to.

**This works identically over remote, unconditionally.** Answering is in remote's ungated Observe tier
(remote §6.2, §12.8) — no capability check, no grant check, no degraded mode, even for an agent whose
grant expired while its session sat parked. The inbox is therefore built with **no remote branch at
all**: it is the one screen where "does this work remotely?" is not a question the code asks.

### 11.4 Notifications, honestly

When `orchestrator.notify` is enabled and a card qualifies, the core sends an ntfy push 60s after the
question stays open. The UI may state that a notification was sent (from `orchestrator.notify.sent`).
It must **never** suggest the notification carried the question content, or that the question can be
answered off the tailnet (remote §12.11) — the payload is a generic wake-up plus a tailnet deep link.
There is no browser push in v1; a closed tab receives nothing over this transport, and the UI does not
imply otherwise.

## 12. The usage view

Three panels, each labelled with its provenance, because runner §7.4's honesty contract is the whole
point of the screen.

**1. What AgentManager used.** Rolling 5-hour and 7-day input/output tokens and session counts from
`GET /api/runner/usage`, rendered with the API's own `disclaimer` string shown in full:

> Counts AgentManager sessions only. Your interactive Claude usage shares the same plan windows and is
> not visible here.

There is **no** percentage, **no** progress ring toward a limit, and **no** "remaining". The design
forbids any component that could be read as a quota, and this is asserted in the acceptance suite as a
literal check (§18, M10): the strings "remaining", "% of plan" and "quota" must not appear in this
screen's output.

**2. Queue and rate limits.** `GET /api/runner/queue` plus live `runner.queue.changed`: running /
queued / blocked / capacity, and each queued session with its position, priority band and
`blocked_reason`. `runner.ratelimited` renders a prominent "cooling until HH:MM" strip with its
`source` label (`observed` / `cli-reported`) — a queue that has silently stopped moving is the worst
failure mode for a background service, so it is never silent here. The capacity control
(`PUT /api/runner/capacity`, clamped 1..8) is present; over the tailnet, raising it is disabled with
the reason "a remote client may lower the cap but not raise it" (runner §15.3 #17).

**3. Per-assignment spend.** A table of open assignments: agents, pattern, phase,
`tokens_used / token_budget` as a bar with the remainder in tokens, rounds used / cap, and an
**estimated model cost** column carrying runner's labelling. A budget is never rendered as money
(orchestrator §16.8); the cost column is a scale hint sitting beside the honest unit.

## 13. Settings, and remote parity

### 13.1 Sections

| Section | Contents |
|---|---|
| **Remote access** (home edition only) | listener status, device tokens, per-agent grants |
| **Runner** | concurrency cap, and a read-only view of queue/timeout config with the layer that won |
| **Notifications** | ntfy topic (a `secretRef` set/unset control, never a value), trigger level, test send |
| **Appearance** | theme: system / light / dark |
| **Logs** | filtered live tail (§13.3) |
| **Health & about** | edition, resolved data root, module list, secret provider (with the degraded-keyfile warning), the `ANTHROPIC_API_KEY` startup warning, versions, and a **Download diagnostics** button |

Config is immutable per process (foundation §2.4), so everything not backed by `settings` is rendered
**read-only with its winning layer** from `GET /api/config/effective` and a note that changing it needs
a restart. Presenting an editable control for something that cannot change at runtime is the fastest
way to make a settings screen untrustworthy.

### 13.2 Remote access

**Listener status** from `GET /api/remote/status`: state, bound address, port, MagicDNS name, Tailscale
backend state, active token count, last error. The `waiting` state renders Tailscale's own state string
("Remote access unavailable — Tailscale is NeedsLogin"), because that is the string that tells the user
what to do.

**Device tokens.** List showing label, prefix, created, last used, last-used peer/node, expiry —
**never the token**. Creation is **local-only** (remote §3.2): at the desk it opens a dialog asking for
a device label, then shows the plaintext **once**, as copyable text and as a **QR rendered
client-side** from the returned `qrUrl` into inline SVG, with a clear "this is the only time you will
see it". Revocation is available everywhere, including from the phone — the "I left my tablet on a
train" case.

**Per-agent grants** from `GET /api/remote/agents`: agent, granted-at, **`expiresAt`**, granted-via,
with a toggle. The same toggle appears on the board card (remote §12.4). Expiry is always shown — a
grant with an invisible deadline is a grant the user will be surprised by.

**Global kill switch** (`PUT /api/remote/enabled`): turning it **off** works from anywhere; turning it
**on** is local-only and renders disabled with that reason over the tailnet. So does **Restart
listener**. This is remote's loosening principle made visible rather than discovered by a 403.

### 13.3 Logs

`GET /api/logs` with level/component/session filters plus `GET /api/logs/stream` for a live tail, a
level control (`PUT /api/logs/level`), and **Download diagnostics** (`/api/logs/download`, fetched to a
blob per §3.1). Deliberately plain: a filterable list, not a log analytics product.

### 13.4 Remote parity — exactly what differs

Everything works over the tailnet except what remote's deny list refuses. The differences, in full:

| Difference | Behaviour |
|---|---|
| **Entry** | A `401` shows the pairing screen: scan the QR from the desktop, or paste. The URL-fragment token is stripped before first render. |
| **Under the hood** | Bearer header on every `/api` call; single-use stream tickets for WS/SSE; avatars and downloads fetched to object URLs. No screen knows. |
| **Denied controls** | **Shown disabled with their reason, never hidden** — Create device token, Enable remote access, Restart listener, Stop background service. The set is read from the deny list enumerated in `GET /api/remote/status` (remote §12.7), not hardcoded, so a future denial greys the right control automatically. |
| **Launch** | May need one extra tap: `409` → grant prompt → automatic retry. Never presented as an error. |
| **Token expiry** | A banner at 14 days remaining. |
| **Notifications** | The app may say a push was sent; it never implies the push carried content or that answering works off the tailnet. |
| **Viewport** | The phone layout of §2.3. |
| **Everything else** | Identical. Answering questions, stopping and pausing sessions, browsing the filesystem for a new project, reading logs, and watching a live session are all first-class remotely. |

### 13.5 Work edition

The question the README asks — how much is disabled or hidden in the work edition versus remote
browser mode — resolves to two different answers, and the difference is principled:

- **Remote browser mode**: the capability *exists* but is *refused for this transport*. Show it
  **disabled with the reason**. The user should learn the boundary, not hunt for a missing button.
- **Work edition**: the remote module is not loaded at all — its routes do not exist (remote §12.6).
  A disabled toggle for a subsystem that is absent is noise, so the **Remote access section is
  hidden**, replaced by one line under Health & about: *"Remote access is not available in the work
  edition."* One honest sentence beats a screen of dead controls.
- **Config-level policy in either edition** — `policy.allowPermissionElevation: false`,
  `orchestrator.notify.enabled: false` — is visible in `/api/config/effective`, so those controls are
  **shown disabled with the reason and the layer that set them**.

Nothing else differs by edition. There is no work-edition code path (D6).

## 14. Visual language and theming

### 14.1 Character without an animation budget

The board should feel like a team, not a table. The warmth comes from cheap, static things:

- **Avatars are large and emoji-first.** A 28px emoji on a coloured disc reads as a face at a glance;
  initials with the agent's own colour are the fallback. This is where nearly all the personality
  lives, and it costs nothing.
- **Taglines are always shown.** One line of the agent's own voice on every card.
- **Specialties are colour-coded** by the closed enum, with the word always present so colour is never
  the only carrier.
- **Copy has a voice.** Empty states read "No agents yet — describe someone in a sentence and Claude
  will draft them", not "No records found".

The animation budget is deliberately small, and it is a budget rather than a taste: transitions
≤150ms, exactly **two** looping indicators in the whole app (the `working` status pulse and the
streaming caret), card lift on drag, and nothing else. No page transitions, no spring physics, no
confetti, no mascots. `prefers-reduced-motion: reduce` disables both loops and every transition.

### 14.2 Tokens, light and dark

One token set, two themes, no third. Semantic tokens only (`--surface`, `--surface-raised`,
`--text`, `--text-muted`, `--accent`, `--border`, `--danger`, `--warn`, `--ok`, plus a
`--specialty-<n>` and a `--status-<n>` ramp). Components never reference a raw colour.

- Light is warm-neutral rather than pure white; dark is a soft charcoal rather than black, so the
  emoji avatars and specialty colours stay legible in both.
- The specialty and status ramps are defined **per theme** and each is contrast-checked against its
  own surface — a hue that works on white is rarely the same hue that works on charcoal.
- Default is **system**; the toggle (system/light/dark) persists in `localStorage` and applies with a
  `data-theme` attribute on the root, so there is no flash on load.

## 15. Accessibility baseline

Non-negotiable for v1:

- **Every drag has a keyboard and a pointer-free equivalent** (§5.4), with dnd-kit's live-region
  announcements for pick-up, target change, drop and cancel.
- **Keyboard reachability** for every action, a visible focus ring on every interactive element,
  logical tab order, `Esc` closing every dialog and sheet, and focus trapped in modals and restored on
  close.
- **Semantic structure**: one `h1` per screen, landmarks (`nav`/`main`/`complementary`), real
  `button`/`a` elements, and lists that are lists.
- **Colour is never the only signal.** Stance is a word, status is a word, specialty is a word,
  disagreement is a labelled banner, outcome is a word.
- **Contrast** meets WCAG AA (4.5:1 body, 3:1 large and UI) in **both** themes; the token file carries
  the measured ratios and the check runs in CI.
- **Live regions, used sparingly.** A polite region announces status transitions ("Priya's session
  finished"), a question arriving, and drag events. Streaming assistant text is **not** announced —
  the transcript region is `aria-live="off"` with a "new output" affordance — because announcing every
  token makes a screen reader unusable.
- **Touch targets** ≥44px on coarse pointers; the phone layouts are designed to that grid.
- **Reduced motion** respected globally.
- **Images**: avatars carry the agent's name as their accessible name; decorative glyphs are
  `aria-hidden`.
- **Zoom** to 200% without horizontal scrolling on every screen except the transcript's code and diff
  blocks, which scroll horizontally inside their own container.

## 16. Performance and limits

- One bundle, code-split by route; the board, the inbox and the session view are the three chunks that
  matter. No runtime CDN, so first load is the full transfer over the tailnet — the budget is < 500 KB
  gzipped for the initial route.
- `session.delta` is coalesced per animation frame; the transcript renders at most 500 blocks with
  **Load earlier**.
- Avatar object URLs are memoised and revoked on eviction.
- The global event feed is filtered **server-side** via `/api/events?types=` (foundation §6.5); per-
  session detail rides its own socket, so a phone never receives another session's deltas and never
  pays radio for bytes it would discard.
- Query `staleTime` is generous (30s+) because invalidation is event-driven; the app polls nothing.

## 17. Architecture conformance

- **D1** — no runtime PowerShell; the frontend is TypeScript served by the Node core; the Electron
  shell is a client (foundation §4.1).
- **D2** — the UI surfaces plan usage as a local estimate with its disclaimer, shows the queue and
  cool-down, and never claims to know the plan window. The `ANTHROPIC_API_KEY` startup warning from
  `/api/health` is displayed persistently.
- **D3** — **one** web frontend, one build, served by the core over HTTP to both Electron and the
  tailnet browser; Electron never loads `file://`. Viewport differences are called out per screen in
  §2.3.
- **D4** — the UI renders assignments as the unit of work everywhere, including the trivial solo one,
  and never mints or routes work itself.
- **D5** — bearer token in a header, stream tickets for WS/SSE, per-agent grant prompt on `409`, denied
  controls shown disabled with reasons, answering never gated.
- **D6** — edition is read from `/api/config/effective` and affects presentation only; there is no
  edition branch in any behaviour, and the remote module is feature-detected, never 404-probed.

## 18. Decisions

Every open question in [README.md](README.md), plus the ones this design had to settle.

**1. Frontend framework — is React confirmed?**
**Yes: React 18 + TypeScript + Vite, TanStack Query for server state, Zustand for the small client
store, dnd-kit for drag and drop, React Router for routing.** The decisive factor is not React itself
but `dnd-kit`: the brief requires drag-and-drop *and* a keyboard/touch equivalent for every gesture,
and dnd-kit is the one mature library that ships pointer, touch and keyboard sensors with screen-reader
announcements. Everything else follows from wanting the smallest conventional stack around it. The
whole state architecture is one sentence: the server is the truth, the event feed is the invalidation
signal, nothing polls.

**2. How does the Electron wrapper stay thin?**
**By owning exactly seven things and loading the app over HTTP** (§1.5): discover-or-spawn the core,
create the window, tray, single-instance, native folder picker, desktop toasts, external links. It
never owns the core (foundation §4.1), never reads the database or transcripts, and never renders
product UI. Loading `http://127.0.0.1:<port>` rather than `file://` is what mechanically prevents
divergence from the tailnet client: same origin model, same relative paths, same bundle, one build.

**3. Terminal-style session rendering (xterm.js) vs structured event rendering, or both?**
**Structured, and xterm.js is rejected.** There is no terminal stream anywhere in the system — runner
emits structured events and writes structured JSONL — so a terminal emulator would require inventing a
text serialisation and parsing it back. The structure is also the value: collapsible tool calls,
diff-aware edits, questions rendered as the card that was answered, and blocks that reflow on a 390px
phone. The one exception is a ~2KB ANSI-SGR formatter for `Bash` **results**, which are genuinely
captured program output; it handles colour and bold and discards everything else. A formatter, not a
terminal.

**4. How much of the UI is disabled or hidden in the work edition vs remote browser mode?**
**Remote browser: disabled with a reason. Work edition: hidden, with one honest sentence.** (§13.5.)
The distinction is whether the capability exists. Over the tailnet, remote's deny list refuses a route
that does exist and that works at the desk — the user must learn that boundary, and the set is read
live from `GET /api/remote/status` so it cannot drift. In the work edition the module is not loaded and
its routes do not exist, so a disabled toggle would be theatre; the Remote section is absent and Health
& about says why. Config-level policy in either edition (`allowPermissionElevation`, `notify.enabled`)
is shown disabled **with the layer that set it**.

**5. What are the drop targets, and what does dropping on an active project mean?**
**Four targets — project, work item, another agent card, the board itself — and dropping on a project
with open assignments creates a *new* assignment, never a reassignment.** (§5.3.) The README left the
"reassign/add the agent" semantics to the design, and the answer is forced by orchestrator: assignment
membership is fixed at creation and `PATCH /api/assignments/:id` explicitly excludes members and
pattern (§11.1). So there is no API for "add this agent to that running collaboration", and inventing
a UI gesture for it would be inventing backend behaviour. What the drop *does* do is surface the
scope-overlap warning before submit, which is the real risk of two agents on one project.

**6. Where does board order live and how is it written?**
**`agent_ui_state.board_order` (roster §2.2), written as a whole ordered list, applied optimistically.**
Roster put it in SQLite precisely so a drag does not produce a git diff. The write path is
`PUT /api/roster/board-order` (roster §9.5) — whole-list, idempotent, one transaction, so a dropped
connection cannot leave a torn order with duplicate or missing positions. This was R2, the one
reconciliation the north star's central gesture could not ship without; it is closed.

**7. How does the UI authenticate streams, and does any screen know?**
**Stream tickets, entirely inside the `EventStream` singleton** (remote §3.4). Screens subscribe to
typed events and never learn whether a ticket was involved. Locally there is no ticket because the
loopback listener has no auth (foundation §6.4), and that asymmetry lives in one file.

**8. How many sockets, and what replays after a disconnect?**
**One always-open global feed, plus one per-session feed while a session view is open, plus the log
stream while the log screen is open.** Reconnect = replay `/api/events?since=<watermark>` **and** tail
the transcript from the stored byte offset, joined on `seq`. Non-persisted events are never expected to
replay (runner §15.2 #12); anything rendered from one must also be derivable from a transcript line.

**9. How do avatars and log downloads authenticate over the tailnet?**
**Fetched with the API client to an object URL / blob**, because `<img src>` and `<a download>` cannot
carry a header. Memoised per agent id, revoked on eviction. No backend change requested — the ticket
mechanism exists for streams, and adding a second ticket flavour for images would be more machinery
than a fetch.

**10. Does the UI ever compute a derived state the server already computes?**
**No, and this is enforced by review**: `disagreement`, `contested`, assignment `outcome`, project
`health`, fleet `state`, effective permissions, and card ordering are all read. Two implementations of
any of them would disagree eventually, and the disagreement would be a bug in the more visible one.

**11. Cost and plan-window presentation.**
**Tokens are the unit; dollars appear only as "estimated model cost"; there is no percentage of
anything.** Runner §7.3 and §15.2 #13 are treated as literal, and the usage screen carries a string
assertion in CI against "remaining" / "% of plan" / "quota" so a well-meaning future change cannot
reintroduce a quota gauge.

**12. Is there a service worker?**
**No.** Remote §3.1's static bypass list anticipates one, but its only v1 purpose would be Web Push,
which is deferred until TLS lands (remote §14). A service worker without push buys offline caching for
an app whose entire value is a live connection to a machine, at the cost of a stale-bundle failure mode
that is miserable to debug over a tailnet. Revisit with Web Push.

**13. Which screens ship the *core loop*, and what is deliberately last?**
**Board → drag → launch → watch → answer is milestones 1–5** (IMPLEMENTATION.md); the Electron shell,
the project page, the wizard, the collaboration view, usage and settings all come after, because a
usable loop in a local browser tab is worth more than a polished shell around nothing.

## 19. Reconciliations raised

Per CLAUDE.md's ground rule these are raised, not silently diverged from. Each is small and additive;
only **R2** blocks a north-star feature. **All seven are now resolved** — each target doc was amended;
the resolution is noted under each item below.

**R1 — foundation §6.4: nobody owns serving the SPA.** Foundation's v1 route inventory lists
`/healthz`, `/api/health`, `/api/config/effective`, `/api/logs*`, `/api/service/shutdown`, `/api/events`
— and no static route — yet the built web bundle ships in `<install>\app\` (§1.2) and remote §3.1's
first middleware rule already bypasses auth for `GET /`, `/assets/*`, `/index.html` and a favicon,
which presupposes they exist. Requested: foundation registers the static handler for the bundle plus an
SPA history fallback (any non-`/api` GET → `index.html`), marked `remote: 'allow'`. Without the
fallback, the ntfy deep link `…/questions/:id` (orchestrator §10) and every bookmarked route 404 on
reload.
**Resolved — see foundation §6.4**: foundation serves the bundle plus an SPA history fallback on both
listeners, `remote: 'allow'`; remote §3.1 rule 1 now names it as the provider.

**R2 — roster §9.1: no write path for `agent_ui_state`.** Roster owns `board_order` and returns it as
`uiState` on `GET /agents`, but the API table has no endpoint that writes it. Drag-to-reorder is the
board's defining gesture and cannot persist. Requested: `PUT /api/roster/board-order { order: string[] }`
(whole-list, idempotent, atomic — a per-card `PATCH` would produce N writes and a torn order on a
dropped connection), plus `PATCH /api/roster/agents/:id/ui-state { pinned }`. **This is the one
reconciliation the north star depends on.**
**Resolved — see roster §9.1 / §9.5** (both endpoints, whole-list atomic write) and roster
IMPLEMENTATION M3, whose acceptance now covers the reorder round-trip.

**R3 — remote §6.2: the per-agent grant gate can be bypassed by the actual launch path.** Remote's
"initiate" tier lists `POST /api/sessions`, `/continue` and `/steer`. But the UI's drag-and-drop launch
calls **`POST /api/assignments/solo`** (orchestrator §16.7, which pins that path explicitly), and a
pattern launch calls `POST /api/assignments`; neither is in the gated tier, so a remote client can
start an agent that has no grant by using the endpoint the product actually uses. Requested: add
`POST /api/assignments`, `POST /api/assignments/solo` and `POST /api/assignments/:id/advance` to the
initiate tier; honour `confirmRemoteAccess` on them; and, because a pattern has ≥2 members, let the
`409 remote_access_required` body carry a **list** of ungranted agents so the client can prompt once
rather than N times. Flagged as security-relevant rather than cosmetic: as written, the grant gate is
not enforced on the launch path.
**Resolved — see remote §6.2 / §6.3**: the initiate tier now covers every session-initiating surface
(`/api/assignments/solo`, `/api/assignments`, `/:id/advance`, the sessions routes) under the stated
principle that the gate binds to launch semantics, not a route name; the 409 body carries the list of
ungranted agents, and remote IMPLEMENTATION §8 tests the solo-assignment refusal.

**R4 — foundation §6.5: `/api/events` has no subscription filter.** All events are fanned out to WS
subscribers, including the high-volume non-persisted ones (`session.delta`, `session.message`,
`session.tool.*`, `session.usage`) for **every** running session. A phone on a metered link holding the
global feed therefore receives token-level deltas it will discard. Requested: an optional type/prefix
filter on the subscription (and the matching `since` replay), so the client can subscribe to lifecycle
and question events only and take per-session detail on runner's dedicated stream. Not blocking — v1
discards client-side — but it is bytes over a radio for no benefit.
**Resolved — see foundation §6.5**: `/api/events` takes an optional `types=` filter (exact types or
`prefix.*`), applied identically to the live stream and the `since=` replay.

**R5 — orchestrator §11.1: the `GET /api/questions` list projection is unspecified.** §16.1 pins what a
card *is* (a `questions` row plus its recommendations) but not what the list returns. Rendering the
inbox needs, per item: `id, kind, status, prompt, options, createdAt, expiresAt, assignmentId,
projectId, sessionId, recommendations[] (agentId, role, stance, strength, rationale), disagreement,
contested, answeredVia`. Requested: that projection on the list endpoint, so a cold phone load is one
request rather than one plus N joins against assignments and roster.
**Resolved — see orchestrator §11.1**, which pins exactly that projection (recommendations embedded,
assignment/project/session ids denormalised) for both the list and the single-question read.

**R6 — runner §11.1: `GET /api/sessions/:id/transcript` cannot tail.** The HTTP route accepts only
`from=<byteOffset>`, while the in-process `getTranscriptTail(sessionId, { maxBytes })` (§11.2) serves
exactly the "last N bytes, whole lines" shape the UI wants when opening a long finished session.
Requested: either a `tail=<bytes>` parameter on the HTTP route, or an explicit rule that a `from` that
lands mid-line advances to the next newline so a client can compute an offset from
`sessions.transcript_bytes` safely. Not blocking — v1 pages forward from 0 — but it makes opening a
500 MB-capped transcript proportional to its size.
**Resolved — see runner §11.1**: the HTTP route gains `tail=<bytes>` *and* the explicit rule that a
`from` landing mid-line advances to the next newline, so both halves of the request are pinned.

**R7 — roster §3.2 / §9.1: `avatar.kind: 'file'` has no write path.** The schema supports a file
avatar and `GET /agents/:id/avatar` serves it, but nothing uploads one, so from the UI the kind is
unreachable. Not blocking: v1 ships emoji and initials, and a PNG placed in the agent folder by hand is
honoured. Requested when file avatars are wanted: `PUT /api/roster/agents/:id/avatar` (multipart,
size- and type-capped, written into the agent folder like any other authored content).
**Resolved — see roster §9.1 / §9.5**: the endpoint writes `avatar.png` into the agent folder and
flips `agent.json` to `kind: 'file'`; roster IMPLEMENTATION M3 carries the acceptance. The *UI* for
it remains deferred (§20) — the API path now exists when it is wanted.

## 20. Deliberately deferred past v1

Aggressively, and named so a later wave does not "discover" them as gaps.

| Deferred | Why / what unblocks it |
|---|---|
| **Avatar upload UI** | The API exists (`PUT /api/roster/agents/:id/avatar`, roster §9.5) — this is a choice, not a gap. Emoji + initials cover the character requirement; the upload screen, cropping and preview are a milestone's work for a cosmetic gain. |
| **`.agentpack` import UI** | Roster's import is a two-phase preview-then-commit flow with collision and missing-secret reporting — a real screen. Export ships as a download; import waits for a real second machine to exist. |
| **Rich agent-permission editor** (rule builder, tool catalogue browser, pattern autocomplete) | v1 edits rule strings as text with validation from the server. A builder needs a tool catalogue the API does not expose. |
| **Work-item board (kanban), priorities, labels, filters** | Projects §7.2 deliberately ships a thin list; a richer UI would imply a tracker the backend is not. |
| **Usage charts and time series** | `usage_events` supports them, but numbers plus one bar answer every v1 question and a chart invites the quota reading runner forbids. |
| **Session diff review / artifact viewer** | Reading the produced file needs a file-read endpoint nobody ships; `GET /api/fs/browse` returns directory names only, by design. |
| **Command palette, global search, saved filters** | Ten routes and one board do not need navigation machinery. |
| **PWA install, offline caching, service worker** | §18 decision 12. Revisit with Web Push once TLS lands. |
| **Browser push notifications** | Needs HTTPS + service worker (remote §14). ntfy is the v1 wake-up. |
| **Multi-window, pop-out session view, always-on-top mini monitor** | Electron's job list stays at seven items. |
| **Theme customisation beyond light/dark, per-agent card colours beyond the avatar** | One token set, two themes, contrast-checked. A theme editor is a product. |

| **Onboarding tour, sample data, guided first-run** | The wizard and quick-add *are* the onboarding if they hit their one-minute targets. |
